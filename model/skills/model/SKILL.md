# Domain Model

把一份逐條的 business rules 文件，變成一份 AI agent 可以直接據此寫 type / class / 測試的**概念層** domain model。

## 定位：規則與資料庫之間的那一層

- **輸入**：`docs/domain/<slug>.md`（由 `business-rules` skill 產出，或人工撰寫的同格式文件）
- **輸出**：`docs/domain/<slug>-model.md`
- **不做**：table 名、欄位型別（`varchar` / `int`）、索引、外鍵、ORM 定義、API 型別。這些屬於「實作提示」與後續的 schema 工作；模型層一旦混入儲存細節，就會被儲存方式牽著走，而不是被規則牽著走。

模型回答的是「領域裡有哪些東西、它們各自守哪些規則、彼此怎麼連、會發生什麼事」；schema 回答的是「怎麼存」。兩者分開，規則改了才知道該改哪一層。

## 核心規則

1. **每個模型元素都能指回至少一條規則 ID；每條規則都能指到至少一個模型元素。** 追溯表是這份文件的骨幹：模型裡多出來的東西是憑空想像，規則裡沒被模型接住的是遺漏。兩邊都要對得上，做不到的列進「未對應」而不是默默略過。
2. **模型不含實作細節。** 型別只用概念型別（見 `references/mapping.md` 的型別表）；不寫 table、欄位命名慣例、nullable、索引。若規則文件的「實作提示」段有這些內容，留在那裡，不搬進模型。
3. **實體 vs 值物件用「身分」判斷，不用「大小」判斷。** 兩個屬性完全相同仍要被視為不同的東西（兩張一模一樣的訂單）是實體；屬性相同就等同（兩個 100 元）是值物件。判斷依據要寫進文件，讓讀者知道為什麼。
4. **不變量掛在能守住它的地方。** 只牽涉單一實體自身屬性的約束掛在該實體；橫跨多個實體的約束掛在聚合根或獨立的 policy，並寫明檢查時機（哪個命令執行前）。
5. **沿用規則文件的詞彙。** 實體、狀態、角色名稱一律用規則文件裡的中文名，再配一個 PascalCase 英文識別名（`訂單 Order`、`已取消 Cancelled`）供程式使用。不另創同義詞；規則文件裡沒有的名稱要標「推導」。
6. **對齊既有程式碼。** 若 repo 已有 domain model、type 定義、schema（TypeScript types / Prisma / Drizzle / zod / OpenAPI）或先前的 `*-model.md`，先讀，沿用既有識別名；衝突處在「與既有模型的關係」段寫明，不自行改既有名稱。
7. **假設要標記並集中列出。** 規則文件裡「來源：假設」的規則所推出的模型元素，在模型裡同樣標「假設」；建模時自己補的判斷（例如把某個屬性抽成值物件）也標「假設」。使用者要能一眼掃過所有可翻案的決定。
8. **提問必須用 `AskUserQuestion`，一次只問一題。** 只問「不同答案會產生不同模型結構」的歧義（例如某個概念是獨立實體還是屬性）；每個選項的 `description` 要寫出選了它模型會長什麼樣、對後續實作的影響。沒有結構性歧義就不問。

## 流程

### Step 0：找到輸入

1. 使用者指定了主題就讀 `docs/domain/<slug>.md`。沒指定時列出 `docs/domain/*.md`（排除 `*-model.md`），只有一份就直接用；多份用 `AskUserQuestion` 問一題選擇。
2. `docs/domain/` 沒有規則文件時，不要憑使用者一句話直接建模——說明需要先有規則文件，建議先用 `business-rules` skill 產出，然後停止。
3. 檢查 repo 是否有可對齊的既有模型或型別（核心規則 6），有就讀。
4. 讀規則文件的「領域拆解」「縮寫表」「狀態流轉」「權限矩陣」「假設清單」，以及每條規則的 ID、類型、陳述、來源。

### Step 1：把規則分派到模型元素

讀 `references/mapping.md`，依規則類型逐條分派：

| 規則類型 | 通常變成 |
|---|---|
| 定義 | 實體 / 值物件 / 列舉；推導值 → 衍生屬性 |
| 約束 | 實體或值物件的不變量；跨實體 → policy |
| 計算 | 衍生屬性或值物件的運算；跨實體 → domain service |
| 狀態流轉 | 狀態列舉 + 實體的狀態機 |
| 權限 | 角色列舉 + 命令的允許執行者 |
| 時間 | 時間點 / 時長屬性 + 排程 policy |
| 觸發 | 領域事件 + 事件處理 policy |
| 例外 | 不變量或 policy 的例外條款 + 優先序 |

分派時同步建立追溯表（規則 ID → 元素）。一條規則可以分派給多個元素（一條狀態流轉規則同時產生狀態列舉值、轉換、事件）。

### Step 2：決定結構

1. **列出候選概念**：領域拆解表的實體、規則陳述裡反覆出現的名詞（金額、時間窗、地址…）。
2. **實體 / 值物件 / 列舉**：依核心規則 3 判斷，寫下理由。有限個固定值的概念（狀態、角色、等級）是列舉。
3. **聚合**：把「同一個不變量必須在同一次操作內守住」的實體圈成一個聚合，選出聚合根；跨聚合只用識別碼參照，不直接持有。一個功能通常只有 1–3 個聚合，超過就檢查是不是把值物件當成了實體。
4. **關聯**：只從規則句型推（`references/mapping.md`「關聯怎麼從規則推出來」），不是名詞一起出現就連線。每條寫：關係名（帶動詞、雙向）、方向、基數、擁有權、跨聚合、建立 / 變更 / 解除時機；掛在關聯上的規則（數量上限、不可換對象）立成不變量或 policy，關聯段引用 ID。
5. **命令與事件**：從「事件 / 動作」列與狀態轉換表推出命令（建立訂單、取消訂單）；每個命令列出執行者、前置條件（引用不變量 ID）、結果、發出的事件。觸發類規則的副作用是事件的處理 policy，不是命令本身的一部分。

### Step 3：釐清（有結構性歧義才做）

只挑同時符合以下條件的問題：

- 不同選擇會產生**不同的模型結構**（多一個實體、聚合邊界不同、關聯方向不同），不只是名稱或屬性差異
- 從規則文件與既有程式碼**推不出**明顯較合理的一邊
- 選錯會讓後續實作需要**大改**（不是加欄位就能補的）

依「選錯的改動成本」排序，一題一題用 `AskUserQuestion` 問；後面的題目若被前面的答案消解就跳過。其餘判斷標「假設」直接寫進文件。

每題寫法：`question` 說明是哪些規則 ID 造成的歧義；`options` 2–4 個，第一個是推薦並標「(Recommended)」；每個 `description` 格式為「模型：〈結構會怎麼長〉／影響：〈對實作、測試、之後擴充的後果〉」。

範例：

```
question: "BR-ORD-003 與 BR-ORD-010 都以「訂單項目」為單位計算，訂單項目要建成獨立實體還是訂單內的值物件？兩種都符合規則，但影響聚合邊界。"
options:
  - label: "訂單內的值物件 (Recommended)"
    description: "模型：OrderItem 是 Order 聚合內的值物件，無獨立身分，隨訂單一起建立與變更／影響：所有數量與金額不變量在 Order 一次守住，實作最單純；但項目無法被其他聚合直接參照"
  - label: "獨立實體（仍在 Order 聚合內）"
    description: "模型：OrderItem 有自己的識別碼，Order 為聚合根／影響：可以指向單一項目（例如部分退款），但每條項目層級的規則要多寫一層身分處理"
```

### Step 4：輸出文件

寫入 `docs/domain/<slug>-model.md`，格式見 `references/template.md`。寫完後做兩個檢查：

1. **追溯完整性**：規則文件每個 BR ID 都出現在追溯表；模型每個元素的「來源」欄至少有一個 BR ID 或標「推導 / 假設」。
2. **無實作細節**：全文搜一次 table、column、varchar、index、foreign key、nullable、ORM 名稱；出現就移到規則文件的「實作提示」或刪掉。

若檔案已存在，用 `AskUserQuestion` 單獨問一題：「合併：更新對應變動的規則，保留其餘 (Recommended)」/「覆蓋」/「另存為 `<slug>-model-YYYY-MM-DD.md`」。合併時沿用既有識別名，變動列進「變更紀錄」。

輸出後在對話中：

1. 摘要：聚合數、實體數、值物件數、列舉數、關聯數、命令數、事件數、不變量數
2. 列出最值得使用者確認的 3 個建模假設（含涉及的 BR ID）
3. 列出「未對應」的規則（若有）並說明原因
4. 提醒下一步：依這份模型建 type / class 與測試；schema 另行設計時以模型為依據，不反向修改模型

## 判斷準則

- `references/mapping.md`：規則類型 → 模型元素的對應細則、關聯的推導句型、概念型別表、實體 / 值物件 / 聚合的判斷準則（Step 1、2 必讀）
- `references/template.md`：輸出文件模板與對話摘要格式（Step 4 必讀）

建模前**務必讀取對應 reference**，不要憑印象分派。
