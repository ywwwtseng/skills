# Impl Fix

`/impl:plan` → `/impl:feature` 這條鏈只能做「還沒有的東西」。專案上線之後，多數工作是修「已經有但不對的東西」，而那條鏈沒有入口。

本 skill 是那個入口。它跟 `/impl:feature` 最大的差別是：**沒有 plan.md 可以照著做，所以第一件事是判斷這個 bug 該不該由你來修。**

## 定位：plan 之外的修復迴路

- **輸入**：一個症狀——使用者回報、CI 失敗、錯誤 log、`/impl:verify` 的 finding、線上異常。
- **輸出**：一個先紅後綠的 regression test、最小範圍的修正、一個 commit（root cause 寫在 body）。
- **不做**：排 task、重構、改規則、補新功能、`git push`。規則要改回 `/domain:business-rules`（或 `/domain:feedback`），範圍大到要設計回 `/impl:plan`。

## 核心規則

1. **先分流，再動手。** 查 `docs/domain/business-rules/` 有沒有管到這個情況：
   - **規則說 A、程式做 B** → 這是 bug，繼續修。
   - **規則沒寫這個情況** → 這不是 bug，是缺規則。停下來，走 `/domain:business-rules` 補規則後再排實作。
   - **程式照規則做了，但使用者期望不同** → 這是規則變更請求，不是 fix。停下來確認要不要改規則。

   無人看守時最危險的失敗不是修不好，是**自己發明一條規則來修**。那條規則不會出現在任何文件裡，而且下一輪會被「修掉」。

2. **沒有一個紅的測試，不准開始改程式。** 重現不出來就是還不知道問題在哪，這時候動手只是在猜。重現不了就停下來問，附上你試過的重現步驟。
3. **修 root cause，不修症狀。** 在錯誤發生的地方補一個 `if` 擋掉，通常只是把問題推到下一層。說得出「為什麼會變成這樣」才動手。
4. **最小改動。** 順手重構、順手改名、順手補型別，會讓「這個 commit 造成了什麼」無法辨識——而修復的 commit 正是之後最常被回溯的那種。看到該改的寫進報告或開一條上游回饋，不要順手。
5. **不改既有測試的預期值。** 既有測試紅了，代表你的修正破壞了別的規則，不是那個測試寫錯了。真的是測試寫錯，那是一條 `規則矛盾` 的上游回饋，停下來提出。
6. **驗收三件事全綠**：新的 regression test 綠、既有測試全綠、typecheck / lint 綠。缺一不可。
7. **同一個 root cause 要查別處有沒有。** 一個誤用的 helper、一個少檢查的邊界，通常不會只犯一次。查一次，同源的一起修（同一個 root cause 算一個邏輯變更）；不同源的記下來，不要一起修。
8. **卡住三次就停。** 同一個錯誤試過 3 次仍無解，或需要外部資訊（帳號、金鑰、線上資料、第三方行為），停下來問，附「卡在哪 / 試過什麼 / 需要什麼才能解」。
9. **root cause 寫進 commit body，不另開文件。** 修復的歷史就是 git 歷史。另開一份 `fixes.md` 只會變成沒有人讀的第二份真相。
10. **範圍失控就換工具。** 要動到超過 3 個檔案、要改介面、要改資料結構、要做資料遷移——這不是 fix，停下來建議回 `/impl:plan` 排成 task。
11. **提問必須用 `AskUserQuestion`，一次只問一題。**

## 流程

### Step 0：把症狀問清楚

需要這些才動得了手，缺了就問（一次一題）：

- **重現步驟**：什麼輸入、什麼操作、什麼環境
- **預期 vs 實際**：使用者認為應該發生什麼，實際發生什麼
- **錯誤訊息 / log**：原文，不要轉述
- **範圍**：只有一個使用者還是全部？一直都這樣還是最近才開始？

「最近才開始」是重要線索——那代表有一個引入問題的 commit，Step 3 可以直接去找它。

### Step 1：分流（核心規則 1）

1. 找相關的 BR：從症狀的領域概念去 `docs/domain/business-rules/` 搜，找到管這個情況的規則。
2. 讀 BR 原文的「輸入 → 預期結果」，跟實際行為比對。
3. 依核心規則 1 的三條分支決定要不要繼續。停下來的那兩種，說明理由並指向對應 skill，**不要順手先把程式改成使用者想要的樣子**。
4. 找不到任何相關規則，但問題明顯是技術性的（空指標、逾時、編碼錯誤、依賴版本），視為 bug 繼續修——規則不管這一層。

### Step 2：用一個紅的測試釘住它

1. 依 repo 既有的測試慣例，寫一個重現這個 bug 的測試。
2. 斷言直接取自 BR 的「輸入 → 預期結果」，並在測試名稱或註解帶上 BR-ID。
3. **跑它，確認它是紅的**，而且失敗訊息就是這個 bug 的症狀（不是因為測試自己寫錯而紅）。
4. 紅不起來 → 回 Step 0，重現條件還沒抓對。

### Step 3：定位 root cause

- 讀相關程式碼，沿著資料流往回走到第一個「值已經不對了」的地方。
- Step 0 顯示「最近才開始」→ `git log -p <相關檔案>`，或 `git bisect` 夾出引入的 commit。看那個 commit 當時想解決什麼，常常會發現這個 bug 是它的副作用。
- 寫得出一句話的 root cause 才往下走：「取消訂單時用了 `createdAt` 而不是 `paidAt` 算退款期限」。寫不出來就是還沒找到，不要開始改。

### Step 4：修

- 只改造成這個 bug 的地方（核心規則 4）。
- 規則的判斷邏輯放回模型層，不要在 controller 或 UI 補一個防禦性的 `if`。
- 不變量的執行落點照 `docs/db/schema.md` 的落點表。

### Step 5：驗收

1. 新的 regression test → 綠。
2. 全部既有測試 → 綠。紅了看核心規則 5。
3. typecheck / lint → 綠。
4. 修不掉就如實說修不掉，附失敗指令與錯誤訊息。試過 3 次 → 核心規則 8。

### Step 6：查同源

用 root cause 的關鍵字掃一次（同一個 helper 的其他呼叫點、同一個欄位的其他使用處、同一類邊界條件）：

- **同源**（同一個 root cause）→ 一起修，一起寫測試，同一個 commit。
- **不同源**（另一個 bug）→ 列進收尾報告，不要順手修。

### Step 7：上游回饋

這個 bug 的成因是設計層的問題時（規則寫得模稜兩可、模型缺一條不變量、schema 落點表說 DB 會擋但實際沒擋），在最相關的 `docs/impl/<feature>/plan.md` 的「上游回饋」表新增一列，狀態 `待處理`，交給 `/domain:feedback`。

沒有對應的 plan.md 就在收尾報告列出來並說明。

### Step 8：commit

呼叫 `/git:commit`。message 用 `fix` type，body 要有兩件事（核心規則 9）：

```
fix(order): 用付款時間而非建立時間計算退款期限

取消訂單時退款期限是從 createdAt 起算，但 BR-order-031 規定從付款完成起算；
草稿停留超過 7 天的訂單一付款就立刻過期。root cause 是 refundWindow() 取錯
欄位，同一個函式在 reportRefunds() 也被呼叫，一併修正。

既有測試沒抓到，是因為測試資料的 createdAt 與 paidAt 一直是同一天。
```

「既有測試為什麼沒抓到」比修正本身更有價值——它指出測試的盲區。

### Step 9：收尾

在對話中：

1. 症狀 → root cause → 修正方式（各一句）
2. 新增的 regression test（檔案與案例）
3. 驗收結果：跑了哪些指令、結果如何（失敗的如實列出）
4. 同源一起修掉的地方
5. 發現但**沒有**修的其他問題（不同源的 bug、該重構的地方）
6. 新增的上游回饋（若有），建議跑 `/domain:feedback`
7. commit hash；沒有 push

## 常見失敗模式

| 症狀 | 為什麼是錯的 |
|---|---|
| 規則沒寫這個情況，就照使用者的話改程式 | 等於發明了一條沒有人知道的規則（核心規則 1） |
| 沒有重現就開始改 | 那是猜，而且改完沒有辦法證明修好了（核心規則 2） |
| 在錯誤噴出來的地方包一個 try / catch | 症狀消失，成因還在，下次在更遠的地方爆（核心規則 3） |
| 修 bug 順便重構那個函式 | 之後回溯「哪個 commit 修了什麼」時分不出來（核心規則 4） |
| 既有測試紅了就改它的預期值 | 你破壞了另一條規則，而不是那個測試寫錯（核心規則 5） |
| 只修使用者報的那一處 | 同一個 root cause 在另外兩個呼叫點還活著（核心規則 7） |
| 一路改到 8 個檔案還在「修 bug」 | 那是設計變更，早該回 `/impl:plan`（核心規則 10） |
| commit message 只寫「修正退款錯誤」 | root cause 與測試盲區沒有留下來，下次還會再犯（核心規則 9） |
