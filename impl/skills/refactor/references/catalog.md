# 技術債分類

每一類：怎麼辨識、安全的改法、什麼時候**不要**改。

共通前提：所有改法都必須在測試保護下進行，而且不准改測試（SKILL 核心規則 1、2）。

## 1. 重複

**辨識**：同一段邏輯出現三次以上。兩次通常還不算——過早抽象比重複更貴。

**安全改法**：抽成函式或模組，呼叫端逐一替換。抽出來的東西放在**它所屬的那一層**（業務規則放模型層，不要放 utils）。

**不要改**：看起來像但語意不同的重複（兩個「7 天」剛好都是 7 天，但一個是退款期限、一個是保固期）。把它們抽在一起，之後其中一個要改成 14 天時會很痛。

## 2. 抽象層級錯

**辨識**：業務規則散進 controller、UI 元件或 SQL；或反過來，傳輸細節（HTTP status、DB 欄位名）滲進模型層。

**安全改法**：把規則的判斷搬回模型層，外層只負責轉換與呼叫。一次搬一條規則，不要整個檔案重寫。

**不要改**：搬完會讓模型層依賴外層的東西（模型開始 import HTTP 或 ORM）。那代表模型缺一個概念——這是 `/domain:feedback` 的事，不是重構。

## 3. 命名

**辨識**：名字與行為不符（`getUser` 會寫入）、縮寫看不懂、同一個概念在不同檔案叫不同名字。

**安全改法**：用編輯器的 rename 一次改完，確認沒有字串引用（log、錯誤碼、序列化欄位）跟著壞。

**不要改**：**公開介面的名字**（匯出的函式、API 欄位、DB 欄位、錯誤碼）。那是破壞性變更，走 `/impl:plan` 或 `/api:contract` 的棄用流程。

## 4. 過長函式 / 過大檔案

**辨識**：一個函式做三件事以上、或要捲動兩次才看得完。

**安全改法**：依「做的事」切，不要依行數切。切出來的每一塊要能單獨命名——命不出名字代表切點不對。

**不要改**：長但線性、而且從頭讀到尾很清楚的函式（一連串的欄位組裝）。切碎它只會讓讀者跳來跳去。

## 5. 缺型別 / 型別過寬

**辨識**：`any`、`unknown` 後面接一堆斷言、用 string 表示列舉、用 number 表示金額。

**安全改法**：由外而內收緊——先把邊界（API 回應、DB 讀取）的型別定準，再往內推。一次收緊一個邊界。

**不要改**：收緊後會需要改測試的（測試在傳不合法的假資料）。那代表型別與實際行為不一致，先確認哪一邊才是對的。

## 6. 測試缺口

**辨識**：`/impl:verify` 報的「有實作無測試」、覆蓋率明顯低的模組、出過 bug 但沒有 regression test 的地方。

**安全改法**：**補測試不是重構**，它是一個 task。本 skill 只負責把它列進 `debt.md` 並標「需先補測試」，讓 `/impl:plan` 排進去。

**不要改**：不要為了提高覆蓋率寫沒有斷言價值的測試（呼叫一次、不驗任何東西）。那會讓覆蓋率好看但抓不到迴歸。

## 7. 過時的相容程式碼

**辨識**：`// 舊版 app 還在用`、feature flag 永遠是同一個值、已棄用欄位的雙寫邏輯。

**安全改法**：先確認**移除條件已成立**（`api/skills/contract/references/compat.md` 的棄用流程：用量降到可接受、最低支援版本已超過它）。條件成立才移除，並同步更新契約的破壞性變更段。

**不要改**：條件沒成立、或查不到用量數據時。查不到就是不知道，不是「應該沒人用了」。

## 8. 死程式碼

**辨識**：沒有任何呼叫者的函式、匯出但沒人 import 的模組、註解掉的區塊。

**安全改法**：確認不是動態呼叫（反射、字串索引、路由表、事件名）之後刪掉。git 會記得它。

**不要改**：對外公開的 API 或 library 匯出（你不知道誰在用）。

## 效能

效能改善**不是重構**——它會改變行為的可觀察特徵（延遲、記憶體、查詢次數）。要做的話：

1. 先有量測（改之前的數字）
2. 當成一個 task 走 `/impl:plan`，有自己的驗收指令
3. 不要混在重構的 commit 裡

唯一的例外是「順手消除的 N+1」這種**明確錯誤**，但仍要單獨一個 commit 並在 body 附上前後的查詢次數。

## 優先級速查

| | 有測試保護 | 無測試保護 |
|---|---|---|
| **收益明確**（已造成 bug / 重複三次 / 下個 feature 會更快） | 先做 | 標「需先補測試」 |
| **收益模糊** | 排在後面，或駁回 | 駁回 |

收益模糊 + 無測試保護 = 直接標 `已駁回` 並寫理由，不要讓它一直躺在清單上製造焦慮。
