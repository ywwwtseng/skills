# Impl Refactor

`/impl:feature` 核心規則 7 和 `/impl:fix` 核心規則 4 都禁止順手改。那是對的——順手改會讓 commit 混入無關變更，還原點就失效了。

但那些被擋下來的東西全寫進備註，然後**沒有任何 skill 消費它們**。這跟「上游回饋寫了沒人讀」是同一種病，只是那個已經由 `/domain:feedback` 治好了。本 skill 是債的那一半。

## 定位：技術債的消費者

- **輸入**：各 `docs/impl/*/plan.md` 的 task 備註、`docs/impl/*/verification.md` 的 `low` findings、`/impl:fix` 報告裡「發現但沒修」的項目、程式碼裡的 `TODO` / `FIXME`，以及使用者直接指出的地方。
- **輸出**：`docs/impl/debt.md`（債的總帳）、行為不變的程式碼改善、每個重構一個 `refactor:` commit。
- **不做**：修 bug（→ `/impl:fix`）、加功能、改公開介面、改上游文件、`git push`。

**這裡開總帳是刻意的**，跟 `/domain:feedback` 不開總帳的理由並不衝突：回饋要回寫它被發現的那份檔案，因為那份檔案還活著；但 `plan.md` 的生命週期到 feature 做完為止，而債是**跨 feature 累積**的——留在已完成的 plan 備註裡，等於沒有人會再看到。

## 核心規則

1. **不准改測試。這是唯一讓重構能無人看守的規則。** 既有測試全部綠、而且**測試檔一個字都沒有被修改**，才叫重構。需要改測試才能過的，那不是重構是改行為——停下來，退回 `/impl:plan` 排成 task。驗收時用 `git diff --stat` 確認測試檔不在 diff 裡。
2. **沒有測試保護就不要重構。** 那段程式碼沒有測試覆蓋時，你改完沒有任何東西能證明行為沒變。要嘛先補測試（那本身是一個 task，不是重構），要嘛跳過並在 `debt.md` 標「需先補測試」。**沒有測試的重構是盲改。**
3. **一次一個重構，一個 commit。** `refactor:` type，body 寫收益與債的來源。不要把三個重構混在一起——那樣出事時無法二分。
4. **不改公開介面。** 函式簽名、匯出的型別、API 形狀、DB schema 一律不動。改了就會動到呼叫端與它們的測試，那是 `/impl:plan` 的範圍。
5. **行為不變包含錯誤行為。** 丟出的例外型別、錯誤訊息的結構、邊界條件的處理，全部要一樣。「順手把錯誤訊息寫清楚一點」不是重構。
6. **說不出收益就不要動。** 收益只有三種算數：下一個 feature 會更快做完、同一段邏輯已經重複第三次、這個抽象層級錯誤已經造成過 bug。「看起來比較乾淨」不是收益——重構沒有收益就只剩風險。
7. **不擴張。** 重構時看到 bug，記進報告交給 `/impl:fix`，不要順手修（這跟 `/impl:fix` 不准順手重構是對稱的）。
8. **每筆債要追溯來源。** 哪個 task 的備註、哪條 finding、哪次 fix 發現的。追不到來源的債通常是「我覺得」，優先級最低。
9. **卡住三次就停。** 同一個重構試了 3 次測試還是紅，還原（`git checkout`）並在 `debt.md` 標「嘗試失敗 — 原因」，不要硬幹。
10. **提問必須用 `AskUserQuestion`，一次只問一題。** 只在「這個抽象值不值得抽」這種需要人判斷價值的事情上問。

## 流程

### Step 0：收齊債

掃四個來源，彙整進 `docs/impl/debt.md`（格式見下）：

1. `docs/impl/*/plan.md` 的 task 備註——找「順手可以改」「暫時這樣寫」「之後要抽出來」這類記錄。
2. `docs/impl/*/verification.md` 的 `low` findings（重複實作、debug 殘留、文件不同步）。
3. `/impl:fix` 報告裡「發現但沒修」的項目。
4. 程式碼裡的 `TODO` / `FIXME`（`grep -rn "TODO\|FIXME" --include` 排除依賴目錄）。

去重：同一段程式碼被多處抱怨時合併成一筆，來源欄列出全部出處——被抱怨三次的通常就是該先做的。

### Step 1：分類與評估

依 `references/catalog.md` 逐筆判定：

| 欄位 | 判定 |
|---|---|
| 類型 | catalog 的八類之一 |
| 收益 | 核心規則 6 的三種之一，寫具體（不是「比較乾淨」） |
| 風險 | 動到幾個檔案、有沒有跨模組、會不會影響效能特徵 |
| 測試保護 | **有 / 部分 / 無**。查那段程式碼有沒有測試覆蓋，這欄決定它能不能做（核心規則 2） |

### Step 2：排序

`收益高 × 風險低 × 有測試保護` 的先做。測試保護是 `無` 的一律不做，標「需先補測試」並在報告建議把補測試排成 task。

一輪做幾個由使用者決定；沒說就做完排序後的前三個然後回報。

### Step 3：逐個執行

每一個都走完這五步，**不要批次進行**：

1. **先跑測試確認是綠的。** 一開始就紅的話，那是 `/impl:fix` 的事，不是重構。
2. 改。只動這一筆債涉及的程式碼。
3. **再跑全部測試**——要全綠。
4. `git diff --stat` 確認**測試檔不在 diff 裡**（核心規則 1）。在的話，還原並退回 `/impl:plan`。
5. typecheck / lint 綠。

紅了就修；試了 3 次還是紅 → `git checkout` 還原這一筆，標「嘗試失敗」（核心規則 9）。

### Step 4：commit

呼叫 `/git:commit`，一個重構一個 commit：

```
refactor(order): 把退款期限計算抽成 refundWindow()

同一段「付款時間 + 7 天」的計算在 cancel、reportRefunds、
orderDetail 三處重複，其中一處曾經取錯欄位（見 fix 3a51640）。
抽成單一函式後只剩一個地方需要正確。

行為不變：既有測試未修改，全部通過。
來源：T-014 備註、verification.md finding #3
```

body 要寫三件事：**收益**、**行為不變的證據**、**債的來源**。

### Step 5：回寫 debt.md

- 狀態 → `已處理` / `嘗試失敗` / `需先補測試` / `已駁回`（含理由）
- 處理結果 → commit hash
- 新發現的債 → 往後接號新增

### Step 6：收尾

1. 收到 N 筆債（自動處理 M / 需先補測試 K / 駁回 J）
2. 每個重構：做了什麼、收益、commit hash
3. 驗收：測試全綠、測試檔未被修改（附 `git diff --stat` 佐證）
4. **發現但沒修的 bug**，建議跑 `/impl:fix`
5. 仍在 `debt.md` 上的項目與它們的阻礙

## debt.md 格式

```markdown
# 技術債

> 最後更新：<YYYY-MM-DD>　|　待處理 <N> / 總數 <M>

| # | 類型 | 位置 | 問題 | 收益 | 測試保護 | 狀態 | 來源 | 處理結果 |
|---|---|---|---|---|---|---|---|---|
| D-001 | 重複 | `src/domain/order.ts` | 退款期限計算重複三處 | 已造成過一次 bug | 有 | 已處理 | T-014 備註、finding #3 | `<hash>` |
| D-002 | 缺測試 | `src/api/webhook.ts` | 沒有任何測試 | — | 無 | 需先補測試 | fix 報告 | |

狀態：`待處理` / `已處理` / `嘗試失敗` / `需先補測試` / `已駁回`
```

## 為什麼不進 `/impl:ship` 的自動迴圈

重構的價值判斷需要人：「這個抽象值不值得抽」沒有客觀答案，而錯誤的抽象比重複更難拆掉。讓它在無人看守時自動去改**已經能正常運作**的程式碼，風險大於收益。

所以 `/impl:ship` 不會叫它。做法是在幾個 feature 之間手動跑一次，或在 `debt.md` 累積到讓你不舒服的時候跑。

## 常見失敗模式

| 症狀 | 為什麼是錯的 |
|---|---|
| 改完測試紅了，就順手把測試改對 | 那不是重構，是改行為，而且沒有人知道行為被改了（核心規則 1） |
| 重構一段沒有測試的程式碼 | 改完沒有任何東西能證明行為沒變（核心規則 2） |
| 一個 commit 裡做完五個重構 | 出事時無法二分，只能整批還原（核心規則 3） |
| 順手把函式簽名改得更漂亮 | 呼叫端與它們的測試都要動，那是 plan 的範圍（核心規則 4） |
| 順手把錯誤訊息寫清楚 | 訊息是行為，客戶端可能在比對它（核心規則 5） |
| 收益寫「程式碼更乾淨」 | 沒有收益就只剩風險（核心規則 6） |
| 重構時看到 bug 順手修掉 | 這個 commit 混入了行為變更，回溯時分不出來（核心規則 7） |
| 把債記在已完成 feature 的 plan 備註裡 | 那份 plan 的生命週期結束了，沒有人會再看到（定位段） |
