# Impl Feature

把 `docs/impl/<feature>/plan.md` 上的 task 一個一個變成已驗證、已提交的程式碼。

## 定位：plan 的執行器

- **輸入**：`docs/impl/<feature>/plan.md`（唯一的指令來源），加上當前 task「來源」欄指到的上游片段（`docs/domain/business-rules/`、`docs/domain/model/`、`docs/db/schema.md`）與「動到」欄列出的既有程式碼。
- **輸出**：程式碼與測試、回寫後的 `plan.md`、每個 task 一個 commit。
- **不做**：規劃（切 task、排順序、改執行序）、改上游文件、`git push`。規劃回 `/impl:plan`，提交交給 `/git:commit`。

plan 回答「照什麼順序做、做完怎麼算過」；本 skill 只回答「現在這一個 task 怎麼做完」。分開的意義是：執行過程中記憶會被壓縮，但下一步要做什麼永遠在檔案裡查得到。

## 核心規則

1. **plan.md 是唯一指令來源。** 沒有 `docs/impl/<feature>/plan.md` 就不要憑一句話開始寫——說明需要先有計畫，建議先跑 `/impl:plan`，然後停止。使用者口頭說的需求與 plan 衝突時，停下來確認要不要改 plan，不要直接照口頭的做。
2. **一次只做一個 task。** 「做完」的定義是三件事都成立：驗收過、plan.md 狀態改成 `done`、commit 建立。缺任何一件都不算完，不可以開始下一個。
3. **狀態先寫再動手，每次變更立刻存檔。** 開工時先把狀態改成 `doing` 並寫入檔案，再開始改程式。不要累積到最後一次更新 plan——中途被中斷的話，沒寫進檔案的進度就是不存在。
4. **只載入這個 task 需要的上下文。** 依「來源」欄只讀被指到的那幾條 BR、那個模型元素、那張 table；依「動到」欄只讀那幾個檔。**不要通讀整份 model 或整個 repo**——context 是 long-running 最稀缺的資源，燒在無關的檔案上會讓後面的 task 無法完成。需要更多才讀更多，並在備註記下「這個 task 其實還需要看 X」。
5. **驗收沒過不准標 `done`，也不准往下一個走。** 驗收 = 該 task 的驗收指令通過 **且** 既有測試沒有變紅。修不掉就改 `blocked`，不要硬幹、不要跳過、不要降低標準。
6. **為了讓測試通過而改測試、改規則、改斷言，是禁止的。** 測試紅了代表程式不符合規則，或這條規則本身有問題。是後者的話寫進「上游回饋」並停下來問，不要靜悄悄把預期值改成實際輸出。
7. **不擴張範圍。** 看到順手能修的 bug、能重構的地方、能補的型別，寫進當前 task 的備註或在 plan 新增一個 task，不要順手改。順手改會讓這個 commit 混入無關變更，還原點就失效了。備註裡的這些記錄之後由 `/impl:refactor` 收齊處理，所以寫清楚位置與理由，不要只寫「這裡很醜」。
8. **照既有程式碼的樣子寫。** 沿用 repo 既有的分層、命名、錯誤處理與測試慣例，遵守 `docs/architecture/tech-stack.md` 的「約束與慣例」。不要引入 plan 與決策文件都沒寫的套件；真的需要就停下來問。
9. **測試案例來自 BR，不是自己想的。** 每條被這個 task 覆蓋的規則，直接把它的「輸入 → 預期結果」寫成斷言，包含規則寫明的邊界與例外。自己補的案例可以加，但 BR 列出的一條都不能少。
10. **卡住要停，不要硬幹。** 同一個錯誤試過 3 次仍無解、需要外部資訊（帳號、金鑰、第三方行為）、或需要使用者決策時，改成 `blocked`，備註寫「卡在哪 / 試過什麼 / 需要什麼才能解」，然後停下來問。持續亂試會燒掉 context 又留不下任何可用的東西。
11. **不改上游文件、不改規劃決策。** 實作中發現規則矛盾、模型缺概念、schema 少欄位，照 plan「上游回饋」表的格式新增一列（狀態 `待處理`）並提出，交給 `/domain:feedback` 處理。發現整個切法錯了，停下來說明並建議重跑 `/impl:plan`，不要邊做邊改執行序。
12. **提問必須用 `AskUserQuestion`，一次只問一題。** 只在 `blocked`、或有「選錯要重做」的實作歧義時問。命名、檔案放哪、要不要抽函式這種改一下就好的事不要問，照既有慣例決定並繼續。

## 流程

### Step 0：定位 task

1. **找 plan**：使用者指定的 feature > `docs/impl/` 下唯一一份 > 有多份就用 `AskUserQuestion` 問是哪一個。都沒有就停（核心規則 1）。
2. **完整讀過 plan.md**：執行協議、驗證指令表、執行序、全部 task、以及**所有備註**。備註是上一輪的記憶，跳過它等於重蹈覆轍。
3. **選 task**：執行序上第一個非 `done` 的。前面有 `blocked` 且未解 → 先處理它，不要跳過去做後面的（跳過會讓依賴它的 task 全部建在空氣上）。
4. **處理 `doing` 殘留**（上一輪被中斷留下的）：
   - 跑 `git status` 看有沒有未提交的產出。
   - 有產出 → 對照 task 的「動到」與備註判斷做到哪，接續完成。判斷不出來時，**問使用者要接續還是丟棄重來**，不要自行 `git checkout` 掉別人的東西。
   - 沒有產出 → 當成沒開始，正常執行。
5. 使用者明確說「只做一個 task」就只做一個；沒說的話依「連續執行」那節走。

### Step 1：載入上下文（只載這個 task 要的）

依核心規則 4，照這個順序讀，讀到夠做就停：

1. task 的「來源」→ 對應的 BR 原文（含輸入 → 預期結果）、模型元素（屬性、不變量、狀態轉換）、schema table（欄位、約束）。
2. task 的「動到」→ 那幾個既有檔案；不存在就是要新建。
3. 一個**既有的相似實作**（同層的另一個 feature）當樣板，抓分層、命名、錯誤處理與測試寫法。
4. `docs/architecture/tech-stack.md` 的「約束與慣例」段與 `docs/architecture/testing.md` 的分層對照（存在的話；整個 session 讀一次就好）。

### Step 2：狀態改 `doing`

把該 task 的狀態改成 `doing`，更新檔案開頭的「最後更新」，存檔。**這一步在寫任何程式碼之前做**（核心規則 3）。

### Step 3：實作

- 只動這個 task「動到」列出的檔案。發現必須動到清單外的檔案：動，但在備註寫明多動了什麼、為什麼——這是給後續 task 的情報（核心規則 2 的「動到與預估不符」）。
- 規則的判斷邏輯放在模型層，不要散進 controller 或 UI；不變量的執行落點照 `docs/db/schema.md` 的落點表（DB 約束的就別在應用層重複實作，應用層的就一定要實作）。
- 寫的過程中不要回頭改已經 `done` 的 task 的產出。真的需要改，那是一個新 task。

### Step 4：測試

- 依核心規則 9，把該 task 覆蓋的每條 BR 的「輸入 → 預期結果」寫成斷言，含邊界與例外分支。
- 測試層照 `docs/architecture/testing.md` 的分層對照（例如落點是 DB 約束的不變量要寫整合測試、打真的測試資料庫，不是 mock）；測試檔位置與命名照 repo 既有慣例。
- 斷言裡帶上 BR-ID（測試名稱或註解），這樣測試紅的時候知道是哪條規則被違反。

### Step 5：驗收

1. 跑該 task「驗收」欄的指令，要通過，且「看到什麼算過」描述的現象要成立。
2. 跑既有測試（plan 驗證指令表的「全部測試」）與 typecheck，**不能變紅**。
3. UI 類的 task 依驗收欄的描述用 `/run` 實際開起來確認。**行動端預設開 iOS 模擬器**（指令以 `CLAUDE.md` 或 `docs/architecture/tech-stack.md` 的「約束與慣例」為準），除非該 task 的驗收明確指定 Android。
4. 沒過就修，修完重跑整組。試過 3 次仍無解 → 進 Step 6 的 `blocked` 分支（核心規則 10）。
5. **如實回報**：修不掉就說修不掉，附上失敗指令與錯誤訊息，不要宣稱完成。

### Step 6：回寫 plan.md

驗收通過：

- 狀態 → `done`
- 「動到」與實際不符 → 在備註更正
- 更新檔案開頭的「進度」與「最後更新」
- 實作中發現的上游問題 → 在「上游回饋」表新增一列（類型、問題、發現於這個 task、狀態 `待處理`）
- 過程中發現需要補的工作 → 在 task 清單末尾新增 task（往後接號，不插隊、不重編），並在「執行序」補上位置

驗收失敗且修不掉：

- 狀態 → `blocked`
- 備註寫三件事：**卡在哪**（具體錯誤訊息）、**試過什麼**（列出嘗試與結果）、**需要什麼才能解**（一個決策 / 一個帳號 / 一段規則澄清）
- 存檔後**停下來問使用者**，不要繼續下一個 task

### Step 7：commit

呼叫 `/git:commit`。commit message 的 scope 或 body 要帶上 task ID：

```
feat(order): 加入訂單狀態轉換 (T-003)
```

這一輪動到的程式碼與 `plan.md` 的狀態更新**放在同一個 commit**——狀態與產出要一起前進，否則回溯時會對不上。

commit 完成，這個 task 才算結束。

### Step 8：連續執行

預設一路做下去，直到以下任一情況才停：

- 全部 task `done` → 進收尾，並建議跑 `/impl:verify`（每個 task 只驗了自己那一塊，整個 feature 的規則覆蓋沒有人檢查過）
- 出現 `blocked` → 停下來問
- 需要使用者決策 → 問完再繼續
- 使用者喊停

每個 task 開始前**重讀 plan.md**（不要憑記憶）——中間可能已經被壓縮過，或使用者改了計畫。對當前 task 的細節有任何不確定，回去讀檔案，不要猜。

要讓它無人值守連續跑，用 `/loop`（不給 interval，讓它自己抓節奏），每輪就是 Step 0–7 一個完整循環。

### Step 9：收尾

在對話中：

1. 這一輪完成了哪些 task（ID + 標題）、各自的 commit hash
2. 建立 / 修改了哪些檔案
3. 驗收結果：跑了哪些指令、結果如何（失敗的如實列出）
4. plan 進度：`done N / 總數 M`，下一個是哪個 task
5. `blocked` 的 task 與卡點（若有）
6. 「上游回饋」（若有），建議跑 `/domain:feedback` 一次收齊處理
7. 下一步：還有 task 未完成 → 再跑一次 `/impl:feature`；全部 `done` → 跑 `/impl:verify` 做規則覆蓋與品質稽核，過了再由 `/git:pr` 開 PR。本 skill 不 push

## 常見失敗模式

| 症狀 | 為什麼是錯的 |
|---|---|
| 一口氣做完好幾個 task 再一起 commit | 還原點消失，其中一個做壞就得整批回退 |
| 測試紅了就改斷言 / 改 BR 讓它綠 | 規則被靜悄悄改掉，而且沒有人知道（核心規則 6） |
| 該 task 驗收綠了，但既有測試紅了還是標 `done` | 下一個 task 會建在壞掉的基礎上（核心規則 5） |
| 備註寫了「已完成」但狀態還是 `doing` | 狀態欄是機器讀的，備註是給人看的；接手的 agent 會重做一遍 |
| 開場先通讀整份 model 與 schema | context 在第一個 task 就燒掉大半（核心規則 4） |
| 邊做邊覺得切法不對，順手改執行序 | plan 與實際產出分岔，之後沒有人知道哪個是真的（核心規則 11） |
| 卡住後反覆嘗試十幾次 | 燒完 context 又留不下可用的東西；三次無解就 `blocked`（核心規則 10） |
