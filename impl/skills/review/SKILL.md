# Impl Review

`/code-review` 主要看 diff 本身寫得對不對，`/simplify` 看哪些可以刪。兩個都沒有專門回答這三件事：

1. **diff 外面**：改了欄位名稱、函式簽名、回傳格式之後，沒被改到的呼叫端還能動嗎？
2. **真實的資料量**：測試只用三筆資料，正式環境有一萬筆的時候怎麼辦？
3. **沒有測試保護的風險**：這次加的邏輯，壞掉的時候有沒有任何測試會紅？

本 skill 專門回答這三件事，而且把每個發現寫成不用回頭讀程式也看得懂的樣子。

## 定位

- **輸入**：一份改動。使用者沒指定就依序找：沒 commit 的改動（`git diff HEAD`）→ 這個分支相對 base branch 的改動（`git diff <base>...HEAD`）。使用者可以直接指定 `uncommitted`、`staged`、`branch`、某個 commit 範圍，或是 PR 網址或編號（`gh pr diff <n>`）。
- **輸出**：在對話中列出發現，最要緊的排第一。不寫檔。
- **不做**：改程式碼、改測試、commit。要修的交給 `/impl:fix`（bug）或 `/impl:feature`（缺工作），能刪的交給 `/simplify`，安全問題建議跑 `/security:audit`。

## 核心規則

1. **只審不改。** 一行就能修好的也不要動手，寫進發現裡。審的人和改的人是同一個人時，這份報告就沒有人會再看第二次。
2. **先讀懂再判斷，不是只讀 diff。** 每一處改到的函式、欄位、型別、設定、路由都要往外找它的使用處（grep 名稱、import、字串 key、序列化的欄位名稱），連沒有被改到的檔案也要讀。這一層就是 diff 看不到的東西，也是本 skill 的價值所在。
3. **負載的判斷要有依據。** 預期的資料量與流量照這個順序找：`docs/architecture/tech-stack.md`、BR 或 plan 寫的數字、schema 的索引與資料表、程式裡的分頁大小與批次上限。都找不到就自己假設一個合理的量級，並在報告開頭寫明「假設 X」，不要停下來問。
4. **每個發現都要寫滿四件事**：程式現在在做什麼、會怎麼出錯（什麼輸入、什麼情況）、怎麼修（具體到檔案與做法）、不修會怎樣（誰會碰到、多常碰到、會不會掉資料）。寫不出「會怎麼出錯」的就不是發現，是感覺，刪掉。
5. **要有證據。** 每個發現附 `path:line`。說呼叫端會壞，就指出是哪一行在讀舊的欄位名稱；說會慢，就指出是哪個迴圈裡的查詢、哪張表沒有索引。
6. **只報真的會出事的。** 風格、命名、「可以更優雅」都不報。同一個根源的多處問題併成一個發現。沒有發現就直接說沒有，不要湊數。
7. **diff 本身的 bug 看到就報，但不用全部掃過。** 完整掃 diff 內的正確性是 `/code-review` 的工作；本 skill 讀程式時順便看到的照樣報，但不要為了這件事把 diff 逐行重讀一次。
8. **提問必須用 `AskUserQuestion`，一次只問一題。** 只在找不到要審的改動、或使用者指定的範圍有兩種讀法時問。

## 流程

### Step 0：確定範圍

1. 依「定位」的順序找出要審的改動，記下是哪一種（沒 commit／分支／PR）。
2. `git diff --stat` 拿到改到的檔案清單。改動是空的就說沒有東西可以審，停止。
3. 讀 `CLAUDE.md`，有 `docs/architecture/tech-stack.md`、`docs/architecture/testing.md` 也讀，抓預期的資料量、測試分層與跑測試的指令。

### Step 1：diff 外的連帶破壞

對每一處**改到介面**的地方（函式簽名、export、型別、欄位名稱、API 的輸入輸出、DB 欄位、設定的 key、事件名稱、路由、CLI 參數）：

1. grep 它的所有使用處，包括字串形式的使用（`row["paid_at"]`、`t('order.title')`、前端打的 API 路徑、測試的 fixture 與 snapshot）。
2. 逐一確認：這個使用處有沒有跟著改？沒改的話，它現在讀到的是什麼？
3. 也查**反方向**：新的程式依賴某個前提（欄位一定有值、陣列不會是空的、某個設定一定存在），呼叫它的地方真的保證得了嗎？

### Step 2：真實資料量

照核心規則 3 定下量級，然後找這些寫法：

| 寫法 | 會怎樣 |
|---|---|
| 迴圈裡打查詢或 API（N+1） | 量一大就慢到逾時 |
| 沒有分頁、沒有上限，一次讀進整張表或整個檔案 | 記憶體爆掉，或回應大到前端卡住 |
| `WHERE`、`JOIN`、`ORDER BY` 用的欄位沒有索引 | 資料一多就全表掃描 |
| 批次處理一筆失敗就整批回滾或整批放棄 | 一千筆裡壞一筆，其他九百九十九筆也沒進去 |
| 默默略過壞掉的資料，沒有記錄也沒有回報 | 資料少了沒有人知道 |
| 沒有逾時的外部呼叫、沒有上限的重試 | 對方一慢，整條請求就跟著卡住 |
| 每個請求都重新計算或重新讀取不會變的東西 | 流量一高就浪費在重複的工作上 |
| 共用狀態沒有鎖、檢查和寫入分成兩步（先查再寫） | 同時兩個請求時資料重複或被蓋掉 |

只報在預期量級下真的會出事的。量級小到不可能碰到的（內部工具、一天幾筆）就不報，或在報告裡寫一句「這個量級下不是問題」。

### Step 3：沒有測試的高風險邏輯

1. 找出這次改動裡的高風險邏輯：有分支或迴圈的判斷、解析外部輸入、金額與數量的計算、權限與身分檢查、狀態轉換、刪除與覆寫資料。
2. 對每一段找測試：照 `testing.md` 的分層與 repo 的測試慣例找對應的測試檔，grep 函式名稱與 BR-ID。
3. 判斷**如果把這段邏輯改錯，有沒有任何一個測試會紅**。只有 happy path 的測試、全部被 mock 掉的測試，都算沒有保護。
4. 沒有保護的列成發現，「怎麼修」寫出要補的那個測試案例（輸入 → 預期結果），不要只寫「補測試」。

### Step 4：排序與收尾

每個發現歸成三級：

- **必修**：正式環境一定或很可能會壞、會掉資料、會擋住使用者（壞掉的呼叫端、預期量級下會逾時、批次整批失敗）。
- **該修**：會出事但條件比較少見，或是高風險邏輯完全沒有測試保護。
- **可以修**：量再大一個級距才會出事，或影響很小。

在對話中照這個格式輸出：

```
審查範圍：<沒 commit 的改動／分支 feat/x 相對 main／PR #12>，<N> 個檔案
負載假設：<依據或「假設 X」>

1. 必修｜Atom feed 每次請求都會 500
   - 現在：`src/models/post.js:14` 把 `publishedAt` 改名成 `publishedOn`
   - 出錯：沒有被改到的 `src/routes/feed.js:31` 還在讀 `post.publishedAt.toISOString()`，拿到 undefined 就丟例外
   - 修法：`feed.js:31` 改讀 `publishedOn`，並在 `feed.test.js` 補一個產生 feed 的測試
   - 不修：所有訂閱 RSS 的讀者都收不到更新，而且目前沒有任何測試會發現

2. 該修｜…

結論：先修 1。
沒審到：<例如「沒跑測試，只讀程式」「沒看前端打這支 API 的地方」「PR 太大，只審了 src/server/」>
```

最後兩行一定要有：**結論**（哪一個先修，或「沒有發現」）與**沒審到**（這次刻意或來不及看的範圍，都看了就寫「無」）。

下一步建議：必修的 bug → `/impl:fix`；缺工作 → `/impl:feature` 或在 plan 補 task；要刪的程式 → `/simplify`；安全相關 → `/security:audit`。
