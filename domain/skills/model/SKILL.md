# Domain Model

把逐條的 business rules 文件，累積成一套 AI agent 可以直接據此寫 type / class / 測試的**概念層** domain model。

## 定位：規則與資料庫之間的那一層

- **輸入**：`docs/domain/business-rules/*.md`（由 `business-rules` skill 產出，或人工撰寫的同格式文件）
- **輸出**：`docs/domain/model/` 目錄——每個聚合一個檔（`order.md`、`customer.md`）、跨聚合共用的值物件與列舉放 `shared.md`、`README.md` 放總覽與追溯表
- **切分方式不同**：規則文件依**功能**分（一個功能一份：`order-dedup.md`、`coupon.md`），模型依**聚合**分（一個聚合一份）。同一個「訂單」會出現在多份規則文件裡，但模型裡只有一個 `Order`；每跑一次本 skill 就把新規則合併進既有模型，而不是另開一份。
- **不做**：table 名、欄位型別（`varchar` / `int`）、索引、外鍵、ORM 定義、API 型別。這些屬於「實作提示」與後續的 schema 工作；模型層一旦混入儲存細節，就會被儲存方式牽著走，而不是被規則牽著走。

模型回答的是「領域裡有哪些東西、它們各自守哪些規則、彼此怎麼連、會發生什麼事」；schema 回答的是「怎麼存」。兩者分開，規則改了才知道該改哪一層。

## 核心規則

1. **每個模型元素都能指回至少一條規則 ID；每條規則都能指到至少一個模型元素。** 追溯表是模型的骨幹：模型裡多出來的東西是憑空想像，規則裡沒被模型接住的是遺漏。兩邊都要對得上，做不到的列進「未對應」而不是默默略過。規則 ID 只在單一規則文件內唯一，跨文件引用一律寫成 `<規則文件 slug>/BR-XXX-nnn`（例：`order-dedup/BR-ORD-003`）。
2. **模型不含實作細節。** 型別只用概念型別（見 `references/mapping.md` 的型別表）；不寫 table、欄位命名慣例、nullable、索引。若規則文件的「實作提示」段有這些內容，留在那裡，不搬進模型。
3. **實體 vs 值物件用「身分」判斷，不用「大小」判斷。** 兩個屬性完全相同仍要被視為不同的東西（兩張一模一樣的訂單）是實體；屬性相同就等同（兩個 100 元）是值物件。判斷依據要寫進文件，讓讀者知道為什麼。
4. **不變量掛在能守住它的地方。** 只牽涉單一實體自身屬性的約束掛在該實體；橫跨多個實體的約束掛在聚合根或獨立的 policy，並寫明檢查時機（哪個命令執行前）。
5. **沿用規則文件的詞彙，跨文件統一。** 實體、狀態、角色名稱一律用規則文件裡的中文名，再配一個 PascalCase 英文識別名（`訂單 Order`、`已取消 Cancelled`）供程式使用。不另創同義詞；規則文件裡沒有的名稱要標「推導」。多份規則文件對同一個概念用了不同名字（「買家」vs「客戶」）時，模型只留一個識別名，其餘在該實體的「別名」列出並註明出處，不要做成兩個實體。
6. **既有模型優先。** `docs/domain/model/` 已有檔案時，它就是模型的現況：沿用既有識別名、ID、聚合邊界，新規則只做新增與修改，並記進「變更紀錄」。新規則與既有元素定義矛盾時不要默默改寫，用 `AskUserQuestion` 問。repo 若有 type 定義、schema（TypeScript types / Prisma / Drizzle / zod / OpenAPI）也一併讀，沿用識別名，衝突處在「與既有模型的關係」段寫明。
7. **假設要標記並集中列出。** 規則文件裡「來源：假設」的規則所推出的模型元素，在模型裡同樣標「假設」；建模時自己補的判斷（例如把某個屬性抽成值物件）也標「假設」。使用者要能一眼掃過所有可翻案的決定。
8. **提問必須用 `AskUserQuestion`，一次只問一題。** 只問「不同答案會產生不同模型結構」的歧義（例如某個概念是獨立實體還是屬性）；每個選項的 `description` 要寫出選了它模型會長什麼樣、對後續實作的影響。沒有結構性歧義就不問。

## 流程

### Step 0：找到輸入與現況

1. 決定這次要處理的規則文件：使用者指定了就以那些為主；沒指定就處理 `docs/domain/business-rules/*.md` 裡**尚未反映在模型裡**的（比對各模型檔「變更紀錄」列出的規則文件與版本），全部都反映過就問使用者要重建哪一份。
2. `docs/domain/business-rules/` 沒有規則文件時，不要憑使用者一句話直接建模——說明需要先有規則文件，建議先用 `business-rules` skill 產出，然後停止。
3. 讀 `docs/domain/model/` 既有全部檔案（核心規則 6），以及 repo 裡可對齊的型別 / schema。
4. 讀每份要處理的規則文件的「領域拆解」「縮寫表」「狀態流轉」「權限矩陣」「假設清單」，以及每條規則的 ID、類型、陳述、來源。
5. **建跨文件實體索引**：每個實體名 → 出現在哪些規則文件、各文件的縮寫、涉及的規則 ID、既有模型裡對應的聚合檔。這張索引決定後面哪些聚合檔要動；被這次規則提到、但既有模型已有的實體，也要把那個聚合檔的相關規則一起讀，否則新舊規則的衝突看不到。

### Step 1：把規則分派到模型元素

讀 `references/mapping.md`，依規則類型逐條分派：

| 規則類型 | 通常變成 |
|---|---|
| 定義 | 實體 / 值物件 / 列舉；推導值 → 衍生屬性 |
| 約束 | 實體或值物件的不變量；跨實體 → policy |
| 計算 | 衍生屬性或值物件的運算；跨實體 → domain service |
| 狀態流轉 | 狀態列舉 + 實體的狀態機 |
| 權限 | 角色列舉 + 命令的允許執行者 |
| 時間 | 時間點 / 時長屬性 + 排程 policy |
| 觸發 | 領域事件 + 事件處理 policy |
| 例外 | 不變量或 policy 的例外條款 + 優先序 |

分派時同步建立追溯表（規則 ID → 元素）。一條規則可以分派給多個元素（一條狀態流轉規則同時產生狀態列舉值、轉換、事件）。

### Step 2：決定結構

1. **列出候選概念**：領域拆解表的實體、規則陳述裡反覆出現的名詞（金額、時間窗、地址…）。
2. **實體 / 值物件 / 列舉**：依核心規則 3 判斷，寫下理由。有限個固定值的概念（狀態、角色、等級）是列舉。
3. **聚合**：把「同一個不變量必須在同一次操作內守住」的實體圈成一個聚合，選出聚合根；跨聚合只用識別碼參照，不直接持有。既有模型已有聚合的，新實體先看能不能歸進去，不要為每份規則文件各開一個聚合；一份規則文件通常只新增 0–2 個聚合，超過就檢查是不是把值物件當成了實體。聚合決定檔案切分：一個聚合一個 `docs/domain/model/<聚合根識別名 kebab-case>.md`。
4. **關聯**：只從規則句型推（`references/mapping.md`「關聯怎麼從規則推出來」），不是名詞一起出現就連線。每條寫：關係名（帶動詞、雙向）、方向、基數、擁有權、跨聚合、建立 / 變更 / 解除時機；掛在關聯上的規則（數量上限、不可換對象）立成不變量或 policy，關聯段引用 ID。
5. **命令與事件**：從「事件 / 動作」列與狀態轉換表推出命令（建立訂單、取消訂單）；每個命令列出執行者、前置條件（引用不變量 ID）、結果、發出的事件。觸發類規則的副作用是事件的處理 policy，不是命令本身的一部分。

### Step 3：釐清（有結構性歧義才做）

只挑同時符合以下條件的問題：

- 不同選擇會產生**不同的模型結構**（多一個實體、聚合邊界不同、關聯方向不同），不只是名稱或屬性差異
- 從規則文件與既有程式碼**推不出**明顯較合理的一邊
- 選錯會讓後續實作需要**大改**（不是加欄位就能補的）

依「選錯的改動成本」排序，一題一題用 `AskUserQuestion` 問；後面的題目若被前面的答案消解就跳過。其餘判斷標「假設」直接寫進文件。

每題寫法：`question` 說明是哪些規則 ID 造成的歧義；`options` 2–4 個，第一個是推薦並標「(Recommended)」；每個 `description` 格式為「模型：〈結構會怎麼長〉／影響：〈對實作、測試、之後擴充的後果〉」。

範例：

```
question: "BR-ORD-003 與 BR-ORD-010 都以「訂單項目」為單位計算，訂單項目要建成獨立實體還是訂單內的值物件？兩種都符合規則，但影響聚合邊界。"
options:
  - label: "訂單內的值物件 (Recommended)"
    description: "模型：OrderItem 是 Order 聚合內的值物件，無獨立身分，隨訂單一起建立與變更／影響：所有數量與金額不變量在 Order 一次守住，實作最單純；但項目無法被其他聚合直接參照"
  - label: "獨立實體（仍在 Order 聚合內）"
    description: "模型：OrderItem 有自己的識別碼，Order 為聚合根／影響：可以指向單一項目（例如部分退款），但每條項目層級的規則要多寫一層身分處理"
```

### Step 4：輸出文件

格式見 `references/template.md`，三種檔案：

| 檔案 | 內容 | 何時動 |
|---|---|---|
| `docs/domain/model/<聚合>.md` | 該聚合的實體、值物件、列舉、不變量、狀態機、關聯、命令、事件、policy、建模假設、變更紀錄 | 這次規則有新增或修改到該聚合的元素 |
| `docs/domain/model/shared.md` | 兩個以上聚合共用的值物件與列舉（金額、幣別、期間…） | 有共用元素新增或修改 |
| `docs/domain/model/README.md` | 總覽 classDiagram、聚合表、跨聚合關聯、跨聚合 policy / service、完整追溯表（依規則文件分組）、未對應規則 | 每次都更新 |

只重寫被影響的檔案；既有聚合檔採合併：沿用 ID 與識別名，新元素接續編號，變動列進該檔「變更紀錄」並註明來自哪份規則文件的哪個版本。新規則與既有元素定義矛盾（例如既有 `Order` 的狀態機沒有新規則要求的轉換、或新規則把值物件當成有身分的東西）時，用 `AskUserQuestion` 問一題：「依新規則修改既有元素 (Recommended)」/「保留既有，新規則列進未決事項」，選項要寫出對其他已依賴該元素的規則文件的影響。

寫完後做兩個檢查：

1. **追溯完整性**：這次處理的每份規則文件的每個 BR ID 都出現在 `README.md` 追溯表；模型每個元素的「來源」欄至少有一個 `<slug>/BR-XXX-nnn` 或標「推導 / 假設」。
2. **無實作細節**：全文搜一次 table、column、varchar、index、foreign key、nullable、ORM 名稱；出現就移到規則文件的「實作提示」或刪掉。

輸出後在對話中：

1. 列出這次新增 / 修改的檔案，各檔一句話說明動了什麼
2. 摘要整套模型現況：聚合數、實體數、值物件數、列舉數、關聯數、命令數、事件數、不變量數
3. 列出最值得使用者確認的 3 個建模假設（含涉及的 `<slug>/BR-XXX-nnn`）
4. 列出「未對應」的規則（若有）並說明原因
5. 提醒下一步：資料庫用 `/db:schema`、對外介面用 `/api:contract`（兩者都以本模型為依據，各自回答「狀態怎麼存」與「外界怎麼呼叫」，都不反向修改模型）

## 判斷準則

- `references/mapping.md`：規則類型 → 模型元素的對應細則、關聯的推導句型、概念型別表、實體 / 值物件 / 聚合的判斷準則（Step 1、2 必讀）
- `references/template.md`：輸出文件模板與對話摘要格式（Step 4 必讀）

建模前**務必讀取對應 reference**，不要憑印象分派。
