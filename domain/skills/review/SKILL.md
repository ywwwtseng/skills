# Business Rules Review

`/domain:business-rules` 負責推導，它會把自己補上的預設標成「假設」，等使用者事後改。本 skill 就是那個「事後改」：一條一條拿給人裁定，裁定完寫回去。

AI 產生的規則文件，真正的問題通常不在單條規則寫錯，而在**規則之間互相打架**、**一個決定會牽動十幾處**、以及**一條新規則開出新的漏洞**。逐條審查的價值在於把這三件事攤在使用者面前，一次只處理一件。

## 定位

- **輸入**：一份規則文件。可以是 `docs/domain/business-rules/<slug>.md`，也可以是使用者上傳或貼上的任何 markdown。
- **輸出**：同一份文件，被裁定過的規則已改寫或刪除，連帶受影響的段落一起改好，變更紀錄補上。
- **不做**：自行推導新規則（那是 `/domain:business-rules` 的事）、改 domain model / schema / 程式碼。

## 核心規則

1. **一次一件事。** 每次只拿一條規則或一個決策給使用者，用 `AskUserQuestion` 問一題，等使用者回答、寫回檔案之後才問下一題。禁止一次丟好幾條。
2. **每條都先給判斷，再給選項。** 判斷最多 3 點，從這四個角度挑有話說的寫：
   - **出處**：這條在需求或其他文件找得到根據嗎？找不到就直說「可能是推測」。
   - **邊界**：哪個例外、數值、觸發時機沒寫清楚。
   - **衝突**：和哪條規則放在一起會打架（例：「每帳號限一個角色」＋「角色可交易」→ 買進角色就破壞上限）。衝突是最該被看見的東西，有就一定要寫。
   - **牽動**：這個決定會影響哪些章節、哪些下游（schema 關係、模組、上線順序）。
3. **選項要寫出後果。** 2–4 個選項，第一個是推薦並標「(Recommended)」，每個 `description` 寫「選了它，規則會變成什麼」。審查常用的四個基本選項是 確認 / 修改 / 刪除 / 待確認；遇到「要選哪一種做法」的決策題，改成列出具體做法。
4. **使用者的回答不一定是選項，照他說的做。**
   - **問「什麼意思」**：用一個具體情境把衝突演一遍（「小明已經有劍士，又在市場買了法師，帳號就有兩個角色」），列出解法，再問一次。不要把原題原封不動再丟一次。
   - **給了選項以外的答案**（「改成即時對戰」）：當作「修改」。先說這個答案會連帶改動哪些規則、多出什麼成本或風險，列出要改的規則草稿；答案本身還有歧義時（PvE 還是 PvP？哪個階段做？）先問清楚，確認後才寫。
   - **要求示意**：選項難用文字想像時（例如兩種戰鬥模式），畫一張示意圖再問。
   - **說「之後處理」**：把這題記進懸置清單，接著審下一條。
5. **裁定完立刻寫回，而且整份一起改。** 一個決定通常不只改一條規則。寫回前先在整份文件搜尋相關字眼（被否決的概念、被改名的東西、引用到這條的地方），所有受影響處一次改完，回報時列出改了哪些章節。只改一條、留下其他地方自相矛盾，比不改更糟。
6. **新的決定可能開出新的漏洞，看到就問。** 例：「技能書可以交易」→ 用錢買書就能跳過學習，違反核心原則。不要自己加規則補洞；把漏洞講清楚、附上建議，當成下一題問。使用者沒回答的漏洞不准寫進文件。
7. **規則需要的觸發時機要定義清楚。** 使用者說「開始學之後就不能交易」，「開始學」要落成可判定的事件（「對書中任一單字送出第一次有效學習提交」），寫進規則並告訴使用者你用了哪個定義，讓他可以改。
8. **ID 不重編、不重用。** 刪除的規則保留號碼不再使用，在「變更紀錄」標記為廢止。
9. **被否決的概念要從正文消失。** 使用者否決的設計（例：不上鏈），正文裡不留刪除線、不留「已移除」佔位、不留「不使用 X」這類為了排除而寫的句子；整份文件讀起來要像一開始就是這樣設計的。歷史只寫在「變更紀錄」。但仍有效的範圍限制要留著（「僅限 PvE」是規則，不是歷史）。使用者要求保留痕跡時照他的意思。
10. **一份文件只審一次。** 審完把狀態寫成 `已審查（日期）`，之後 `/impl:plan` 才會接受這份文件。狀態已經是 `已審查`（或舊格式的 `已確認`）的文件不再審：說明這份已審過、審查日期，然後停止。只有使用者明確說「重新審」才再跑一次。
11. **數值不寫死在規則裡。** 來自補習班經驗、網路文章、平衡性猜測的數字，規則只寫「要有上限 / 要標註程度」，具體數字放設定檔或標為待確認。使用者自己拍板的數字（「死亡扣 10%」）照寫。

## 流程

### Step 0：讀取與盤點

1. 讀整份規則文件，先看標頭的「狀態」：
   - `已審查` / `已確認` → 已審過，依核心規則 10 停止。
   - `審查中` → 續審：從第一條還沒裁定的規則接著做，不從頭來。
   - `待審查` / `草稿` / 沒有狀態 → 把狀態改成 `審查中`（沒有標頭的外來文件，在標題下補一行 `> 狀態：審查中`），開始審。

   同目錄或 `docs/` 下有需求、產品、domain model 文件時一起讀，作為判斷「出處」的依據。
2. 盤點三類東西，向使用者報一行數量：
   - **決策題**：文件裡寫著「待定案」「開發前必須決定」「A 或 B？」的項目。
   - **有編號的規則**：`BR-xxx`。
   - **沒有編號的條目**：散落在各章節的規則句。
3. 若規則沒有編號，不先改格式；照現有結構審，審到時再處理。

### Step 1：先審決策題

決策題通常會牽動大量規則（角色數量會改到交易、資產、市場、上線順序）。先把它們定案，後面逐條審時很多條會自動有答案，或直接消失。

決策題的排序：牽動範圍越大越前面。後面的題目被前面的答案消解（不上鏈 → 「要不要發鏈上代幣」自動有答案），直接標為定案並告訴使用者，不再問。

### Step 2：逐條審規則

從第一條未審的規則開始，依文件順序往下。每條：

1. 規則原文
2. Claude 的判斷（核心規則 2）
3. `AskUserQuestion` 一題（核心規則 3）
4. 依回答處理（核心規則 4–7），寫回檔案

**每 10 條停一次**，回報進度（已審 / 剩餘 / 懸置），問要繼續還是先停。進度就在檔案裡，下次從未審的接著做。

使用者額外丟來的參考資料（例如一份單字量統計）：先分成「會變成規則的」和「只是背景知識的」，用表格說明每個概念適合放在哪一章、會變成什麼規則，列出需要先決定的設計問題，等使用者決定後才寫進文件。

### Step 3：收尾

1. 每條規則都裁定過（含「待確認」）時，把狀態改成 `已審查（YYYY-MM-DD）`。使用者中途喊停、還有規則沒審時，狀態維持 `審查中`，下次續審。
2. 在「變更紀錄」加一列，摘要這輪審查改了什麼。文件是 `/domain:business-rules` 格式時，同步更新「假設清單」與「未決事項」：使用者確認的假設，來源改為「需求」並從假設清單移除；懸置的題目寫進「未決事項」。
3. 在對話中輸出：

   ```
   狀態：已審查（YYYY-MM-DD）／ 審查中（剩 R 條）
   已審 N 條：確認 a ／ 修改 b ／ 刪除 c ／ 待確認 d
   決策題 M 題，已定案 k 題
   懸置：
   - <題目>（為什麼還不能決定）
   審查中發現、尚未處理的漏洞：
   - <漏洞>
   ```

4. 已經有 `docs/domain/model/` 或 `docs/db/schema.md` 時，提醒這輪改動會影響下游，建議接著跑 `/domain:model`（或交給 `/domain:feedback` 追漣漪）。本 skill 不自己改下游。

## 判斷準則

- 規則格式、ID 規範、陳述句寫法：沿用 `/domain:business-rules` 的 `references/writing-rules.md`。改寫規則時照那份的寫法，不另立格式。
- 文件不是 `/domain:business-rules` 格式時，保留原文件的格式，只改內容；不要趁審查把整份改成另一種格式，除非使用者要求。
