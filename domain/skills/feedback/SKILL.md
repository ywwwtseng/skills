# Domain Feedback

`/impl:plan`、`/impl:feature`、`/impl:verify` 都會把「規則有矛盾、模型缺概念、schema 少欄位」寫進上游回饋，然後繼續做自己的事。**沒有任何一步會回頭讀它**。

本 skill 是那些回饋的消費者。沒有它，無人看守跑得越久，文件與程式碼分岔得越遠，而且沒有人知道。

## 定位：把實作的發現送回設計

- **輸入**：`docs/impl/*/plan.md` 的「上游回饋」表（**全部 feature，不是只有一個**）、`docs/impl/*/verification.md` 的上游回饋與 findings、`blocked` task 備註裡「需要什麼才能解」那一句，以及使用者口頭提的規則問題。
- **輸出**：被修正的上游文件（由對應 skill 改）、回寫狀態與處理結果的回饋表、因漣漪被標回 `todo` 的 task。
- **不做**：改產品程式碼與測試、自行裁定一條規則應該長什麼樣、下 git 指令、開 PR。

`/impl:feature` 回答「這個 task 怎麼做完」；本 skill 回答「實作時發現設計錯了，那個錯要怎麼回到設計裡」。

## 核心規則

1. **一次掃全部 feature。** 同一個規則缺口常常被好幾個 feature 各自撞到一次。只處理眼前那一份 plan，會把同一條問題修三遍、或修成三種樣子。
2. **回饋的真相留在原處，不另開總帳。** 處理結果寫回它被發現的那份 `plan.md` / `verification.md`。開一份 `docs/domain/feedback.md` 當總帳，等於製造第二份真相，下次沒有人知道該信哪一份。
3. **分類決定路由，分類錯全錯。** 五類：`規則矛盾`（兩條 BR 互相牴觸）／`規則缺漏`（實作遇到的情況 BR 沒寫）／`模型缺概念`（規則講得出但模型沒有這個元素或不變量）／`schema 缺欄位或落點錯`（模型有但存不下來、或落點表寫 DB 擋實際擋不住）／`誤報`（實作看錯了，規則本身沒問題）。判不出類型就是資訊不足，回去讀那條 BR 原文，不要猜。
4. **規則的裁定是產品決策，一定要人決定——但不要一條一條擋住。** 順序是：先把不需要裁定的全部處理完，再把需要裁定的整理成一份清單，依影響排序，用 `AskUserQuestion` 一題一題問完。無人看守時，在第一條就停下來等人，等於整輪什麼都沒做。
5. **改上游一定有漣漪，必須追到底。** `BR → model → schema → plan 的 task`。補了一條規則卻沒有人去實作它，比不補更糟：文件說有、程式沒有，而且覆蓋表看起來是綠的。受影響且已 `done` 的 task 一律標回 `todo` 並寫明原因。
6. **不自己動手改上游文件，呼叫對應 skill 改。** 每份文件只能有一個作者，`business-rules.md` 的作者永遠是 `/domain:business-rules`。繞過去直接編輯，會寫出不符合那份文件格式與 ID 規則的內容。
7. **駁回也要留理由。** 判定為誤報的標 `已駁回` 並寫清楚為什麼（「BR-order-012 已涵蓋這個情況，實作看的是舊版本」）。沒有理由的駁回，下一輪會被重新提一次。
8. **提問必須用 `AskUserQuestion`，一次只問一題。** 每題的 `options` 要寫明「規則會變成什麼」＋「會動到哪些 BR / 模型元素 / table / 已完成的 task」，第一個標「(Recommended)」。

## 回饋表格式

這張表是本 skill 的介面。`/impl:plan`、`/impl:feature`、`/impl:verify` 只負責新增「待處理」的列，狀態欄只有本 skill 維護：

```markdown
## 上游回饋

| # | 類型 | 問題 | 發現於 | 狀態 | 處理結果 |
|---|---|---|---|---|---|
| F-001 | 規則缺漏 | 訂單付款後、出貨前取消時退款怎麼算，BR 沒有寫 | T-007 | 待處理 | |
| F-002 | 誤報 | 以為 BR-order-012 沒處理零元訂單 | T-003 | 已駁回 | BR-order-012 第 3 點已涵蓋 |
```

- **#**：`F-001` 起，每份檔案內部連號，永不重編
- **類型**：核心規則 3 的五類之一
- **發現於**：task ID、verification finding 編號，或「使用者回報」
- **狀態**：`待處理` / `處理中` / `已處理` / `已駁回`
- **處理結果**：指向產出（`新增 BR-order-021`、`order.md#Order.refundPolicy`、`schema.md#refunds`），或駁回理由

## 流程

### Step 0：收齊

1. 掃 `docs/impl/*/plan.md` 的「上游回饋」表，取所有 `待處理` 與 `處理中` 的列。
2. 掃 `docs/impl/*/verification.md` 的上游回饋段與 `high` / `medium` findings 裡屬於設計問題的那些。
3. 掃所有 `blocked` task 的備註，「需要什麼才能解」是一段規則澄清的，收進來。
4. **去重**：同一個問題在多個 feature 被提出時合併成一條，來源欄列出全部出處。合併後的處理結果要寫回每一個出處。

一條 `待處理` 都沒有 → 說明沒有待處理的回饋，停止。不要為了有事做而去翻文件找問題。

### Step 1：分類與定性

逐條判定：

| 欄位 | 判定方式 |
|---|---|
| 類型 | 核心規則 3 的五類。先讀那條 BR 的原文再判，不要只看回饋的描述 |
| 嚴重度 | `high`＝已經寫進程式碼的行為是錯的／`medium`＝擋住某個 `blocked` task／`low`＝純文件缺漏，程式沒受影響 |
| 要不要人裁定 | 「這條規則應該是什麼」需要產品決策 → 要；「文件漏寫一個已經談定的東西」→ 不要 |

判為 `誤報` 的，在這一步就標 `已駁回` 並寫理由（核心規則 7），不進後面的流程。

### Step 2：排序

`high` → 擋住 `blocked` task 的 → `medium` → `low`。同級時，影響的 task 多的先。

### Step 3：處理不需裁定的

逐條呼叫對應 skill，讓它改它自己的文件（核心規則 6）：

| 類型 | 交給誰 |
|---|---|
| 規則缺漏 / 規則矛盾 | `/domain:business-rules` |
| 模型缺概念 | `/domain:model` |
| schema 缺欄位或落點錯 | `/db:schema` |

呼叫時要帶：問題原文、相關的 BR-ID 與模型元素、實作當時實際遇到的情況（那是最有價值的部分——它是真實世界的輸入）。

### Step 4：裁定需要人決定的

把 Step 1 標為「要裁定」的整理成清單，依 Step 2 的順序，用 `AskUserQuestion` 一題一題問（核心規則 4、8）。

每題：

- 問題描述帶上**實作遇到的具體情況**，不要只講抽象規則
- `options` 2–4 個，每個寫「規則變成什麼／會動到哪些 BR、模型元素、table、已完成的 task」
- 第一個標「(Recommended)」，並說明推薦的理由

答完後同樣走 Step 3 的路由，交給對應 skill 落成文件。

### Step 5：追漣漪

每條處理完，順著鏈往下追一次，**不要跳過**（核心規則 5）：

1. **BR 改了** → `docs/domain/model/` 有沒有元素或不變量要跟著改？有 → `/domain:model`。
2. **模型改了** → `docs/db/schema.md` 有沒有 table / 欄位 / 約束 / 落點要跟著改？有 → `/db:schema`。
3. **上面任一項改了** → 哪些 `plan.md` 的 task 的「來源」指到被改的元素？
   - 狀態 `done` → 標回 `todo`，備註寫「因 F-00X（<一句話>）需要重做：<具體要改什麼>」
   - 狀態 `todo` → 在備註提醒來源已變更
   - 規則覆蓋表裡對應的列，狀態改成待確認
4. **新增了規則但沒有任何 task 覆蓋它** → 在最相關的 `plan.md` 末尾新增 task（往後接號、不插隊、不重編），來源指向新的 BR-ID。

### Step 6：回寫

每一條（含合併前的每個出處）：

- 狀態 → `已處理` / `已駁回`
- 處理結果 → 指向實際產出的 BR-ID、模型元素、table，或駁回理由
- 受影響的 plan 更新「變更紀錄」，寫明是哪條回饋造成的

### Step 7：收尾

在對話中：

1. 收到 N 條：自動處理 M ／裁定後處理 K ／駁回 J ／仍待處理 L（附原因）
2. 改了哪些上游文件，各自新增 / 修改了什麼（BR-ID、模型元素、table）
3. **漣漪**：被標回 `todo` 的 task（ID + 原因）、新增的 task
4. 下一步：`/impl:feature` 重跑受影響的 task → `/impl:verify` 重驗覆蓋 → `/git:pr`
5. 仍需使用者決策但這輪沒問完的，列出來

## 常見失敗模式

| 症狀 | 為什麼是錯的 |
|---|---|
| 只處理眼前這份 plan 的回饋 | 同一條規則缺口在別的 feature 被修成另一個樣子（核心規則 1） |
| 補了規則，但沒有人去實作它 | 文件說有、程式沒有，覆蓋表還是綠的——比不補更糟（核心規則 5） |
| 自己決定規則應該是什麼 | 那是產品決策，agent 編出來的規則沒有人知道它是編的（核心規則 4） |
| 為了不打擾使用者，第一條就停下來等人 | 不需要裁定的那 8 條也一起停了（核心規則 4 的順序） |
| 直接編輯 `business-rules.md` | 寫出不符合該文件 ID 規則與格式的內容（核心規則 6） |
| 開一份 `docs/domain/feedback.md` 當總帳 | 第二份真相；下次沒有人知道該信哪一份（核心規則 2） |
| 駁回時只寫「不是問題」 | 下一輪會被原封不動地重新提一次（核心規則 7） |
