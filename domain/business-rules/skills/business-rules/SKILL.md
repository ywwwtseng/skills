# Business Rules

把一段問題描述 + 功能願望，變成一份逐條、可驗證的 business rules 文件。

## 前提：使用者只提供問題與功能，其餘由你推導

使用者的輸入通常只有兩件事：

1. **要解決什麼問題**（例：「客戶常常重複下單，客服要手動退款」）
2. **想要什麼功能**（例：「同一客戶 5 分鐘內相同商品只能下一單」）

你要做的是**推導**，不是**訪談**。使用者不會也不想逐條回答規則細節，因此：

- 邊界條件、例外、預設值由你依 `references/` 的 checklist 主動補齊，並標為「假設」
- 只有「不同答案會導致不同規則、且無法從常理推出合理預設」的歧義才提問
- 每一份文件都要能讓 AI agent 直接據此實作與寫測試，不需再回頭問人

## 核心規則

1. **先推導再提問。** 一律先讀完輸入、產出完整草稿，再看草稿裡哪些假設風險高到值得問。禁止一開始就丟問題。
2. **提問必須用 `AskUserQuestion`，一次只問一題，等使用者選完再問下一題。** 每題 2–4 個選項，第一個選項是你的推薦預設並標「(Recommended)」；每個選項的 `description` 必須寫出「選了它，規則會變成什麼」（會新增 / 刪除 / 改寫哪些規則、對使用者或資料的後果），不能只寫選項名稱。禁止在同一次 `AskUserQuestion` 塞多題。沒有重大歧義就不問，直接輸出。
3. **每條規則都要可驗證。** 必須寫得出「輸入 → 預期結果」的範例；寫不出來的不是規則，是願望，放進「未決事項」。
4. **規則不含實作細節。** 不寫 table 名、API 路徑、框架；寫「訂單」不寫 `orders` table。實作對應放在文件最後的「實作提示」段，與規則分開。
5. **一條規則只講一件事。** 「A 且 B 時不可 C，但 D 例外」要拆成主規則 + 例外規則，各自有 ID。
6. **每條規則標注來源**：`需求`（使用者明說）/ `推導`（由需求邏輯必然推出）/ `假設`（你補的預設，使用者可改）。假設要集中列一次，方便使用者一眼掃過。
7. **對齊專案既有詞彙。** 若 repo 已有 `docs/domain/business-rules/`、`docs/domain/model/`、`docs/tech-stack.md`、schema（Prisma / Drizzle / SQL / zod / OpenAPI）或 domain model，先讀取，沿用既有實體與狀態名稱，不另創同義詞；與既有規則衝突時在「與既有規則的關係」段寫明。
8. **規則之間的衝突要有優先序。** 兩條規則可能同時適用而結論不同時，明確寫出誰優先，並補一個同時觸發的範例。

## 流程

### Step 0：讀取脈絡

1. 讀使用者輸入，抽出：問題（痛點）、功能（願望）、明說的限制。
2. 檢查 repo 是否有可對齊的資料（見核心規則 7），有就讀。
3. 決定文件 slug：以主要實體或功能命名，kebab-case（例：`order-dedup`、`coupon`、`membership-tier`）。

### Step 1：拆解領域（在對話中列出，不提問）

用一張短表列出：

| 面向 | 內容 |
|---|---|
| 參與者 | 誰會觸發或受規則影響（買家、客服、系統排程…） |
| 實體 | 規則作用的對象及其關鍵屬性（訂單：金額、狀態、建立時間…） |
| 事件 / 動作 | 會觸發規則檢查的時間點（送出訂單、退款、每日 00:00…） |
| 狀態 | 實體有生命週期時列出所有狀態（草稿 → 已送出 → 已付款 → …） |

這張表是規則的骨架；後面每條規則都要能指回這裡的某個實體 + 事件。

### Step 2：依類別推導規則

讀 `references/rule-categories.md`，**逐類別走一遍** checklist，對這個功能適用的就寫規則，不適用的跳過。順序固定：

1. 定義與推導值
2. 約束與驗證
3. 計算
4. 狀態流轉
5. 權限
6. 時間與排程
7. 觸發與副作用
8. 例外與覆寫

每條規則格式見 `references/writing-rules.md`。寫完後讀 `references/edge-cases.md`，針對涉及的面向（金額、時間、數量、並發、刪除、身分…）逐項檢查是否遺漏，遺漏就補規則或補進「假設」。

### Step 3：釐清（有必要才做）

檢視草稿中標為「假設」的項目，只挑出同時符合以下三點的：

- 不同選擇會產生**不同的規則**（不只是參數不同）
- 從問題描述與常理**推不出**明顯較合理的一邊
- 選錯會讓功能**無法用**或造成**資料 / 金錢錯誤**

符合的先依「選錯的損害大小」排序，再**一題一題**用 `AskUserQuestion` 問：每次呼叫只放一題，等使用者選完、把答案套回草稿後，才問下一題；後面的題目若被前面的答案消解，就跳過不問。全部問完才進 Step 4。其餘假設不問，直接寫進文件讓使用者事後改。

每一題的寫法：

- `question`：說明這個歧義出現在哪條規則（附草稿中的規則 ID），以及為什麼推不出預設
- `options`：2–4 個，第一個是推薦預設並標「(Recommended)」
- 每個 `option.description`：寫出選了它之後的**規則影響**，格式為「規則：〈規則會怎麼寫〉／影響：〈對使用者、資料或金額的後果〉」，不同選項的影響必須看得出差異

範例（一題）：

```
question: "CON-002 的 5 分鐘窗口，要用哪種計算方式？從問題描述推不出客戶預期的是哪一種。"
options:
  - label: "滑動窗口 (Recommended)"
    description: "規則：以「上一張相同訂單的建立時間 + 5 分鐘」為界／影響：連續下單會被持續阻擋，最能防重複，但客戶每次重試都會重置等待時間"
  - label: "固定區間"
    description: "規則：以每 5 分鐘為一格（00:00–00:05…），同格內只允許一單／影響：實作簡單，但跨格邊界（00:04:59 與 00:05:01）會放行兩單"
```

常見值得問的例子：時間窗口是「滑動」還是「固定區間」、限制是「阻擋」還是「警告後放行」、金額進位規則、既有資料是否適用新規則（回溯）。

### Step 4：輸出文件

寫入 `docs/domain/business-rules/<slug>.md`，格式見 `references/template.md`。

若檔案已存在，用 `AskUserQuestion` 單獨問一題（同樣每個選項要寫影響）：「合併：新增與修改規則，保留其餘 (Recommended)」/「覆蓋」/「另存為 `<slug>-YYYY-MM-DD.md`」。合併時保留既有 ID，新規則接續編號，被修改的規則在「變更紀錄」列出。

輸出後在對話中：

1. 摘要規則數量（各類別幾條）與假設數量
2. 列出最需要使用者確認的 3 個假設（含 ID）
3. 提醒可再呼叫本 skill 針對某條規則或某個例外情境擴充

## 判斷準則

- `references/rule-categories.md`：八大類別定義、每類的 checklist 與範例（Step 2 必讀）
- `references/writing-rules.md`：規則格式、ID 規範、陳述句寫法、決策表、優先序
- `references/edge-cases.md`：依面向整理的邊界條件 checklist（Step 2 末必讀）
- `references/template.md`：輸出文件模板

推導前**務必讀取對應 reference**，不要憑印象列規則。
