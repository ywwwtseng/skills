# UI Preview

`/ui:screens` 寫的是文字，`/ui:calm-ui`、`/ui:tonal-ui` 寫的是規則。使用者第一次真正**看到**畫面，是在 `/impl:feature` 已經把 API、狀態、資料流都接好之後——那時候說「這裡排版不對」，要改的就不只是版面。

本 skill 把「看到畫面」提前到排計畫之前，而且做出來的東西不丟：預覽稿就是正式的畫面元件，之後只是把假資料換成真資料。

## 定位

```
/ui:screens → /ui:preview → /impl:plan → /impl:feature → /impl:verify
（文字規格）  （看得到、改到確認）  （UI task 驗收 = 跟確認稿一致）
```

- **輸入**：`docs/ui/screens/<畫面>.md`（顯示什麼、動作、狀態矩陣、所屬介面）、該介面選定的 `/ui:calm-ui` 或 `/ui:tonal-ui`、`CLAUDE.md` / `docs/architecture/tech-stack.md`（技術棧、開發指令、UI 風格對照）、既有元件與 token。
- **輸出**：畫面元件（只吃 props）+ 每個狀態一組假資料 + dev-only 預覽路由（程式碼）；`docs/ui/preview/<畫面>/` 的確認截圖與 `docs/ui/preview/<畫面>.md` 紀錄。
- **不做**：接 API、寫 store / query / mutation、業務邏輯、改 `docs/ui/screens/` 的內容、改 token 的值。

## 兩種模式

| 呼叫 | 什麼時候 | 做什麼 |
|---|---|---|
| `/ui:preview <畫面>` | 畫面還沒實作（`/ui:screens` 之後、`/impl:plan` 之前） | 從規格做出元件與預覽路由，迭代到確認 |
| `/ui:preview tweak <畫面>` | 畫面已經實作、要調整 | 改前截圖 → 改 → 改後截圖，對照迭代到確認 |

沒帶參數時：列出 `docs/ui/screens/` 裡還沒有確認稿的畫面讓使用者選（`AskUserQuestion`）；使用者講的是「某個畫面要改」就走 tweak。一次處理一個畫面，多個畫面就一個一個來。

## 核心規則

1. **預覽稿就是正式元件。** 畫面元件只接 props（資料、狀態、callback），不 import API client、store、router 的資料層。預覽路由餵假資料；`/impl:feature` 之後寫一個容器把真資料接進同一個元件。做一份「看看就好」的 mockup 再重寫一次，等於確認稿跟實作之間沒有任何保證。
2. **每個狀態都要看得到。** 規格狀態矩陣裡的每一列（載入、空、篩選後沒結果、錯誤、權限不足、離線、送出中、送出失敗……）都要有一組假資料與一張截圖，寫「不適用」的除外。只給使用者看 happy path，等於只確認了最不會出問題的那一張。
3. **假資料要像真的，也要有最壞情況。** 用真實長度的名字、金額、日期，不用 `Lorem ipsum`、`Test User`、`123`。另外每個列表 / 卡片類畫面加一組「最壞情況」：超長名字、超長無空白的 email、單字元名字、0 筆、999+ 筆、很大的數字。版面在最壞情況下破掉，是預覽階段最值得抓到的事。操作後的回饋（已複製、開關切換、送出中、成功 toast、失敗訊息）也算狀態，各給一組假資料並截圖——使用者要看得到按下去之後長什麼樣。
4. **先自己過一遍再給使用者看。** 截圖後先用 Read 打開每張圖，照該介面視覺語言 skill 的交件前檢查清單逐項看，加上 safe area、44×44pt 點擊區、互動元素沒被蓋住（行動端與會在手機上打開的畫面）、每個按鈕與選單項目都有對應的回饋狀態。自己看得出來的問題先修掉，不要讓使用者幫你抓「按鈕貼著動態島」這種事。
5. **只用 token，不寫死值。** 顏色、字級、間距、圓角一律引用該介面的 token。使用者說「再淡一點」「再大一點」→ 換成相鄰的 token；token 裡沒有適合的值 → 停下來說明，問要不要調整 token（會影響整個介面）還是這裡當例外並記進紀錄。不在元件裡寫 `#9A9A9A` 或 `text-[15px]`。
6. **只改外觀，不改內容。** 版面、層級、間距、文案語氣、元件選擇、動效可以照回饋改。同一個動作只換呈現方式（原地展開 ↔ 對話框、頁面 ↔ 底部面板）也算外觀，直接改，畫面規格的「確認方式」跟著更新一行即可。使用者要求的改動會讓畫面**多顯示或少顯示一個欄位、多或少一個動作、改變導航**時，那是規格變了：停下來說明，建議回 `/ui:screens` 改規格，不要在預覽稿裡偷偷加——那個欄位在模型和契約裡可能根本不存在。
7. **回饋跟視覺語言衝突時，講清楚再照使用者的。** 例如在 calm-ui 的介面要求「每則加一張卡片」。說明它違反哪一條、會有什麼後果，使用者仍要這樣做就照做，並記進紀錄的「例外」，`/impl:verify` 才不會把它當 finding。
8. **確認才算數，而且要確認在檔案裡。** 使用者說「可以」才把截圖鎖進 `docs/ui/preview/<畫面>/`，並寫紀錄。對話裡的「看起來不錯」不會傳到下一個 session。
9. **預覽路由不能進正式環境。** 路由加上環境判斷，正式 build 打開就是 404 或導回首頁。
10. **提問用 `AskUserQuestion`。** 每輪給完對照圖後問一次：`確認` / `要改`（Other 寫要改什麼）/ `先停`。不要每改一個小地方就問一次，同一輪的回饋全部改完再截圖。

## 流程

### Step 0：讀規格、確認介面與技術棧

1. 讀 `docs/ui/screens/<畫面>.md`：所屬介面、顯示、動作、版面骨架、狀態矩陣、錯誤行為。沒有這份規格 → 停，建議先跑 `/ui:screens`。tweak 模式沒有規格也可以進行，但要在紀錄寫明「無規格」，且核心規則 6 改成「不改畫面目前顯示的內容與動作」。
2. 從規格標頭（或 `CLAUDE.md` 的 UI 風格對照）確認介面與視覺語言，用 Skill 載入那一套（`/ui:calm-ui` 或 `/ui:tonal-ui`）。
3. 確認技術棧與開發指令（`CLAUDE.md` 的約束與慣例、`docs/architecture/tech-stack.md`、`package.json`）。找對應的預覽路由寫法與截圖方式：`references/setup.md`。
4. 這個介面還沒有 token → 先把該 skill 的 `references/tokens.css` 落成 theme（跟 `/impl:plan` 的 design foundation task 做的是同一件事），否則截出來的不是這套風格。
5. 讀 `docs/ui/preview/<畫面>.md`（存在的話）：上一次確認了什麼、有哪些例外，這次延續。

### Step 1：做元件、假資料、預覽路由

照 `references/setup.md` 的該技術棧寫法：

1. **畫面元件**：放在專案既有的元件 / 畫面目錄，命名照既有慣例。props 的型別從規格的「顯示」與「動作」推（欄位名稱對齊模型與契約），狀態用一個 prop 表達（例如 `state: 'loading' | 'empty' | 'error' | 'ready' | …`）或拆成既有慣例的形式。
2. **假資料**：`<畫面>.fixtures.ts`（或該語言的等價物），一個狀態一組，加上核心規則 3 的最壞情況。
3. **預覽路由**：`dev-preview/<畫面>?state=<狀態>`，一個網址一個狀態，加上核心規則 9 的環境判斷。
4. 跑 typecheck，要過。

tweak 模式：先跑 Step 2 拍「改前」（存到 repo 外的暫存目錄），再照回饋改既有元件。畫面元件跟資料層綁在一起、無法單獨餵假資料 → 不在這裡重構；直接在開發環境操作到那個狀態截圖，並在紀錄寫明，建議之後 `/impl:refactor` 拆開。

### Step 2：截圖與對照頁

1. 啟動開發環境（`/run` 或專案的開發指令）。
2. 每個狀態 × 每個寬度截一張，檔名 `<狀態>--<寬度>.png`（例如 `empty--mobile.png`）。寬度：
   - 使用者端 Web：`mobile`（390×844）與 `desktop`（1440×900）
   - console・後台：`desktop`（1440×900）與 `mobile`（390×844）——後台也會在手機上打開
   - 行動 App：iOS 模擬器（有動態島的機型），需要時加 Android
   - calm-ui 的介面用深色截；有淺色模式的再加一組
3. 核心規則 4：先自己看過、修掉明顯問題，修完重截。
4. 產生對照頁 `docs/ui/preview/<畫面>/index.html`（格式見 `references/record.md`），用 `open` 在瀏覽器打開。tweak 模式的對照頁是「改前 / 改後」兩欄。Web 專案另外附上預覽路由的網址，使用者可以直接在瀏覽器裡縮放、hover、點擊。

### Step 3：迭代

1. `AskUserQuestion`：`確認` / `要改` / `先停`。
2. `要改` → 把回饋逐條分類：外觀（直接改）、內容或導航（核心規則 6，停下來說明）、跟視覺語言衝突（核心規則 7）、token 沒有適合的值（核心規則 5）。同一輪的外觀回饋全部改完，回 Step 2 重截。
3. `先停` → 寫紀錄，狀態 `草稿`，記下還沒處理的回饋，下次從這裡接。
4. 同一個地方改了三輪還在來回 → 換個方式問：做兩三個版本並排在對照頁上讓使用者選，不要再猜。

### Step 4（可選）：在 Figma 裡改

只有在工具清單裡有 Figma MCP、且有「把網頁擷取 / 轉換成 Figma 設計」這類寫入工具時才提供。沒有就跳過，不要特地提。

1. 第一輪對照頁給出去時，順便問要不要把畫面丟進 Figma 直接改。
2. 要 → 把預覽路由的每個狀態擷取進 Figma，給使用者連結。
3. 使用者改完 → 用讀取工具（先 `get_metadata` 找到被改的 frame，再對那個 frame 取 `get_design_context` 與 `get_screenshot`）讀回來，跟目前的截圖比對，把差異翻譯成**token 層級**的改動（間距從 16 變 24 → 換成對應的間距 token），對不到 token 的照核心規則 5 處理。不要把 Figma 輸出的程式碼直接貼進專案。
4. 回 Step 2 重截，確認改完的程式碼跟 Figma 一致。

Figma 只是改的地方；確認稿永遠是程式碼截出來的圖。

### Step 5：鎖定確認稿

使用者選 `確認` 後：

1. 最後一輪的截圖留在 `docs/ui/preview/<畫面>/`，刪掉沒有對應到目前狀態的舊截圖。
2. 寫 `docs/ui/preview/<畫面>.md`（格式見 `references/record.md`）：狀態 `已確認`、日期、元件與假資料與預覽路由的路徑、截圖清單、迭代中做的決定、例外、轉給 `/ui:screens` 的內容改動。
3. tweak 模式且這個畫面已有確認稿 → 用新的截圖取代，紀錄的「歷次調整」加一列。

### Step 6：收尾

1. 改了哪些檔案（元件、假資料、預覽路由、`docs/ui/preview/`）
2. 確認了幾個狀態 × 幾個寬度；有沒有寫「不適用」而沒截的狀態
3. 例外與待 `/ui:screens` 處理的內容改動
4. 下一步：
   - 預覽模式 → 下一個畫面繼續 `/ui:preview`，或全部確認後跑 `/impl:plan`（它會把 UI task 改成「把資料接到已確認的元件」，驗收對照確認稿）
   - tweak 模式 → 改動照 `CLAUDE.md` 的交付流程處理
   - 有內容改動 → 先跑 `/ui:screens` 改規格，再回來確認

## 判斷準則

- `references/setup.md`：各技術棧的元件 / 假資料 / 預覽路由寫法、環境判斷、截圖指令（Step 1、2 必讀）
- `references/record.md`：對照頁與 `docs/ui/preview/<畫面>.md` 的格式（Step 2、5 必讀）

## 常見失敗模式

| 症狀 | 為什麼是錯的 |
|---|---|
| 做一份 HTML mockup 或獨立的 prototype 給使用者看 | 確認的是另一份東西，實作時重寫一次就不保證一樣（核心規則 1） |
| 只截 happy path | 空、錯誤、最壞情況才是最常破版的地方（核心規則 2、3） |
| 假資料都是「Test User」「123」 | 真實長度的資料一進來版面就變了，確認稿失真（核心規則 3） |
| 截完直接丟給使用者 | 違反檢查清單的明顯問題應該自己先修（核心規則 4） |
| 使用者說「淡一點」就寫一個新色碼 | token 失效，下一個畫面又不一樣（核心規則 5） |
| 使用者說「這裡加顯示運費」就加上去 | 那是規格改動，運費在模型裡可能不存在（核心規則 6） |
| 對話裡說好了但沒寫紀錄 | 下一個 session 和 `/impl:verify` 都不知道確認過什麼（核心規則 8） |
| 預覽路由在正式站打得開 | 假資料與未完成的畫面對外公開（核心規則 9） |
| 每改一個 padding 就問一次 | 使用者被問到放棄；同一輪改完再給（核心規則 10） |
