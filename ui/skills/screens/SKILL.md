# UI Screens

`/ui:tonal-ui` 回答「長什麼樣」，但「有哪些畫面、每個畫面在各種狀態下顯示什麼」沒有任何文件回答。於是 UI 的 task 就是：plan 寫「做取消訂單的畫面」，`/impl:feature` 打開一條 BR 和一個 model，然後自由發揮。

問題不在版面醜，在於**狀態沒有人定義**。BR 寫了「超過 7 天不能取消」，畫面上那個按鈕是 disabled、是隱藏、還是按下去才報錯？三種都能通過 typecheck，三種使用者體驗完全不同，而且兩個 task 會給出兩種答案。

## 定位：規則與畫面之間的那一層

- **輸入**：`docs/domain/business-rules/`（規則與失敗情境）、`docs/domain/model/`（命令、查詢、狀態機、權限）、`docs/api/contract.md`（端點、錯誤碼、分頁——存在的話）、`docs/architecture/tech-stack.md`（有哪些客戶端平台）、既有畫面與元件。
- **輸出**：`docs/ui/screens/<畫面>.md`（一個畫面一份，像 model 依聚合分檔）+ `docs/ui/screens/README.md`（畫面地圖、導航規則、全域狀態與行為）。
- **不做**：視覺設計（顏色、字級、間距、圓角 → `/ui:tonal-ui`）、元件實作、API 設計（→ `/api:contract`）、資料庫。

`/api:contract` 回答「客戶端能呼叫什麼」；本 skill 回答「使用者在螢幕上看到什麼、能做什麼」。

## 核心規則

1. **畫面不能顯示模型沒有的東西，也不能觸發契約沒有的操作。** 每個畫面元素追溯到模型元素或 `BR-ID`，每個動作追溯到一個命令與一個端點。畫面需要但上游沒有的，回報並交給 `/domain:feedback`，不要在畫面規格裡發明一個欄位——那個欄位沒有人知道它從哪來。
2. **狀態是規格的主體，不是附註。** 每個畫面都要走完 `references/states.md` 的狀態清單。只寫 happy path 的畫面規格等於沒寫：實作時 agent 一樣要自己發明空狀態與錯誤處理，而且每個 task 發明的不一樣。
3. **每個錯誤碼都要有畫面行為。** 逐條走 `docs/api/contract.md` 的錯誤碼表：這個錯誤發生時使用者看到什麼、能做什麼（重試？回上一頁？重新登入？）。沒有定義的錯誤碼，App 只會顯示「發生錯誤」，而使用者不知道該怎麼辦。
4. **行動端的狀態比 web 多，而且不能省略。** 離線、送出中斷網、背景喚醒後資料已過期、權限被拒、從推播或深連結直接進入某個畫面、鍵盤遮擋、返回手勢。這些在 web 上很少出現，在 App 上天天發生——不寫，實作就會漏。
5. **不做視覺設計。** 資訊層級、版面骨架、元素順序、優先顯示什麼要寫；顏色、字級、間距、圓角一律交給 `/ui:tonal-ui`。兩份文件不重疊。
6. **導航是全域決策，寫在 README。** 返回去哪、登入後去哪、深連結進入時的返回堆疊、跨流程的中斷與回復——寫一次，所有畫面共用。讓每個畫面各自決定，App 就會出現走不出去的死路。
7. **一個畫面一份檔案，一個流程一張圖。** 畫面之間的關係放 README 的畫面地圖；單一畫面的細節放它自己的檔案。
8. **不改上游文件。** 設計畫面時發現規則沒定義某個情境、模型缺一個查詢、契約缺一個端點，寫進最相關的 `docs/impl/<feature>/plan.md` 的「上游回饋」表（狀態 `待處理`），交給 `/domain:feedback`。
9. **提問必須用 `AskUserQuestion`，一次只問一題。** 只問「會產生不同畫面數量或不同流程」的（這個操作要獨立一頁還是彈窗、列表要不要支援批次選取、註冊要不要分步）。按鈕文案、元素順序這類事自己決定並寫進規格。

## 流程

### Step 0：讀上游、確認平台、盤點既有

1. 讀 `docs/domain/model/`，整理出**命令**（誰能做、前置條件）、**查詢**（篩選與排序）、**狀態機**（每個狀態下能做什麼）。沒有模型就停，建議先跑 `/domain:model`。
2. 讀 `docs/domain/business-rules/`，把**失敗情境**單獨列出來，Step 5 要逐條指派畫面行為。
3. 讀 `docs/api/contract.md` 的端點與錯誤碼表（存在的話）。沒有契約時可以繼續，但要在 README 記明畫面是在沒有契約的情況下設計的，而且資料來源欄先留空。
4. 確認客戶端平台（iOS / Android / web / 桌面）。有行動端 → `references/states.md` 的行動端段全部必寫（核心規則 4）。
5. 盤點既有畫面與元件：既有 `docs/ui/screens/`、路由表、既有頁面。沿用既有命名與導航慣例，只做增量。

### Step 1：推導畫面清單

從模型推，不要從想像推：

| 模型元素 | 畫面 |
|---|---|
| 一個查詢（列表） | 一個列表畫面（含篩選、排序、分頁、空狀態） |
| 一個查詢（單筆） | 一個詳情畫面 |
| 一個建立命令 | 一個表單畫面（或詳情畫面上的表單區） |
| 一個狀態轉換命令 | 詳情畫面上的一個動作（依 Step 4 決定 disabled / 隱藏 / 可按但會報錯） |
| 聚合內的實體 | 詳情畫面裡的區塊，或它自己的子畫面 |
| 權限規則 | 不是畫面，是每個畫面與動作的可見性條件 |

一個命令不一定是一個畫面；但**每個命令都要能在某個畫面被觸發**，找不到歸屬的列進「未落地」並寫原因。

### Step 2：導航與進入點

寫進 README：

- **畫面地圖**：畫面之間怎麼走（一張圖或一張表），標出進入點（首頁、分頁、推播、深連結）。
- **返回規則**：每個畫面的返回去哪；從深連結或推播直接進入時，返回堆疊怎麼組。
- **流程中斷與回復**：多步驟流程中途離開，草稿保留嗎、下次從哪開始。
- **登入邊界**：哪些畫面需要登入，未登入時進入會怎樣，登入完回到原本要去的地方嗎。

### Step 3：每個畫面的內容

逐個畫面寫（格式見 `references/template.md`）：

- **用途**：一句話，使用者來這裡是要做什麼。
- **進入點**：從哪裡來。
- **顯示**：哪些模型元素、資料來自哪個端點。逐項標來源。
- **動作**：可觸發哪些命令，各自對應哪個端點、需要什麼權限、什麼條件下不可用。
- **版面骨架**：資訊層級與元素順序（不含顏色字級）。

### Step 4：狀態矩陣

逐個畫面走完 `references/states.md`。每個狀態回答三題：**顯示什麼**、**使用者能做什麼**、**資料怎麼來**。

不適用的狀態明確寫「不適用」並給理由，不要留空——留空的分不出是「不需要」還是「忘了寫」。

動作的**不可用**要三選一並寫理由：

| 做法 | 什麼時候用 |
|---|---|
| **隱藏** | 這個使用者永遠不會有這個權限 |
| **disabled + 說明** | 條件暫時不成立，使用者可以理解並改變它（「還有 3 天可取消」） |
| **可按，按了才報錯** | 條件依賴伺服器端的即時狀態，客戶端算不準 |

預設 disabled + 說明；客戶端狀態可能過期的一律「可按，按了才報錯」——客戶端的資料永遠可能是舊的。

### Step 5：錯誤行為

逐條走契約的錯誤碼表（核心規則 3），每條寫：**畫面上出現在哪**（整頁 / 行內 / toast / 對話框）、**訊息說什麼**、**使用者能做什麼**（重試、修正輸入、回上一頁、重新登入、聯絡客服）。

沒有契約時，改成逐條走 BR 的失敗情境。

### Step 6：釐清（有結構性歧義才做）

只挑「不同選擇會產生不同畫面數量或不同流程」的問題，依重做成本排序，一題一題問。`options` 的 `description` 格式：「畫面：〈會變成幾個畫面、怎麼走〉／影響：〈使用者要多按幾次、實作代價〉」。

### Step 7：輸出

寫入 `docs/ui/screens/`。寫完做四個檢查：

1. **追溯完整性**：每個顯示元素有來源、每個動作對應一個命令與端點；模型的每個命令都能在某個畫面被觸發。
2. **狀態完整性**：每個畫面的狀態清單都走完了，沒有留空。
3. **錯誤覆蓋**：契約的每個錯誤碼都有畫面行為（或明確寫「此畫面不會發生」）。
4. **導航無死路**：每個畫面都走得出去，深連結進入也有返回路徑。

### Step 8：收尾

1. 寫入 / 修改的檔案
2. 規模：畫面數、動作數、錯誤碼覆蓋數
3. 覆蓋統計：模型命令 N 個，能在畫面觸發 M 個（未落地逐條列原因）
4. 最值得確認的 3 個流程假設
5. 上游回饋（若有），建議跑 `/domain:feedback`
6. 下一步：`/impl:plan` 讀本文件排 UI 的 task（驗收欄可以直接寫「在 X 狀態下顯示 Y」）；視覺套用 `/ui:tonal-ui`

## 判斷準則

- `references/states.md`：每個畫面都要走完的狀態清單，含行動端特有狀態與表單狀態（Step 4 必讀）
- `references/template.md`：`README.md` 與 `<畫面>.md` 的輸出模板（Step 7 必讀）

## 常見失敗模式

| 症狀 | 為什麼是錯的 |
|---|---|
| 只寫 happy path 的畫面 | 實作時一樣要自己發明空狀態與錯誤處理（核心規則 2） |
| 錯誤一律「發生錯誤，請稍後再試」 | 使用者不知道該怎麼辦，而契約明明分得出來（核心規則 3） |
| 行動端沒寫離線與送出中斷網 | App 上天天發生，不寫就會漏（核心規則 4） |
| 在畫面規格裡寫顏色與字級 | 跟 `/ui:tonal-ui` 重疊，兩份會分岔（核心規則 5） |
| 每個畫面各自決定返回去哪 | App 出現走不出去的死路（核心規則 6） |
| 動作不可用時一律隱藏 | 使用者不知道為什麼看不到，也不知道怎麼讓它出現（Step 4） |
| 畫面顯示一個模型沒有的欄位 | 那個欄位沒有人知道從哪來、誰維護（核心規則 1） |
