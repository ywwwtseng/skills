# 模型 → 契約的對應

模型元素怎麼變成操作、欄位與錯誤碼。轉換前務必讀這份，不要憑印象決定端點長相。

## 命令 → 操作

| 模型的命令 | 操作 | 說明 |
|---|---|---|
| 建立某實體 | `POST /<複數資源>` | 回 201 與建立後的表示 |
| 修改屬性 | `PATCH /<資源>/{id}` | 只帶要改的欄位；全量覆寫才用 `PUT` |
| 狀態轉換 | `POST /<資源>/{id}/<動詞>` | **一個轉換一個端點**（`/cancel`、`/submit`、`/approve`） |
| 刪除 | `DELETE /<資源>/{id}` | 軟刪照 schema 的策略，回 204 |
| 聚合內實體的操作 | `POST /<根>/{id}/<子資源>` | 層級對應聚合邊界 |
| 批次操作 | `POST /<資源>/batch:<動詞>` | 只在模型真的有批次命令時才做，並定義部分失敗怎麼回 |

**狀態轉換不要做成 `PATCH {status: "cancelled"}`。** 理由三個：哪些轉換合法講不清楚（客戶端要自己知道狀態機）、每個轉換的權限不同但同一個端點只能有一組權限、每個轉換的失敗原因不同但錯誤碼混在一起。模型的狀態機有幾條轉換，就有幾個端點。

命令的**前置條件**（模型寫的「只有在 X 狀態才能做」）一律變成一個錯誤碼，不是讓客戶端自己判斷後就不呼叫——客戶端的狀態永遠可能是舊的。

## 查詢 → 操作

| 模型的查詢 | 操作 |
|---|---|
| 依識別碼取單一 | `GET /<資源>/{id}` |
| 列表 + 篩選 | `GET /<資源>?<篩選>` |
| 跨聚合的報表 / 統計 | 獨立的讀取端點，不要塞進實體資源 |

- 篩選參數只開模型或 BR 真的需要的那幾個，而且每個都要有索引支撐（對照 `docs/db/schema.md` 的索引表）。想不出哪個畫面會用的篩選就不要開。
- 分頁預設 cursor（穩定、不會因為插入而跳頁），資料量小且需要跳頁時才用 offset。二選一全份統一。
- 排序欄位列白名單，不接受任意欄位名。

## 欄位

| 模型 | 契約 |
|---|---|
| 識別碼 | 字串（即使 DB 是整數也回字串，之後換主鍵策略才不會是破壞性變更） |
| 可選〈型別〉 | 可選欄位；「沒有值代表什麼」寫進說明 |
| 值物件（單一值） | 巢狀物件（`{"amount": "120.00", "currency": "TWD"}`），不要攤平成 `total_amount` / `total_currency` —— 契約不是 table |
| 值物件（集合） | 陣列 |
| 列舉 | 字串常數，值與模型一致；**不要回數字** |
| 狀態 | 字串常數 + 可選的 `allowedTransitions`（讓客戶端知道現在能做什麼，省一次往返） |
| 衍生屬性 | 回或不回都可以，但要標明它是算出來的，客戶端不可回傳 |
| 時間 | ISO 8601 帶時區 |
| 金額 | 照 schema 的單位慣例；用字串或整數最小單位，**不要用浮點數** |

**response 不是 table 的投影。** 只回客戶端需要的欄位，而且刻意隔一層——否則 schema 加一個內部欄位就洩漏出去，改一個欄位名就變成破壞性變更。

## 錯誤碼

每個錯誤碼一列：`錯誤碼 | HTTP status | 何時發生 | 客戶端該怎麼處理 | 來源`。

錯誤碼命名用穩定的常數（`ORDER_CANCEL_WINDOW_EXPIRED`），不是訊息。訊息會被翻譯、會被改，錯誤碼不會。

### status 選擇

| 情境 | status |
|---|---|
| 參數格式錯、缺必填 | 400 |
| 未認證 / token 過期 | 401 |
| 已認證但沒有權限 | 403 |
| 資源不存在 | 404 |
| 業務規則不允許（狀態不對、期限過了、額度不足） | 409（衝突）或 422（語意不可處理）—— 二選一全份統一 |
| 唯一性衝突 | 409 |
| 冪等鍵重複但參數不同 | 409 |
| 超過限流 | 429 |
| 伺服器錯誤 | 500 |

**業務規則失敗不要回 400。** 400 的意思是「你的請求寫錯了」，但「超過 7 天不能取消」的請求寫得完全正確，只是現在不允許。客戶端要靠這個差別決定是修正輸入重送，還是顯示一則訊息。

### 錯誤 envelope

全域一種形狀，例如：

```json
{
  "error": {
    "code": "ORDER_CANCEL_WINDOW_EXPIRED",
    "message": "訂單已超過可取消期限",
    "details": { "paidAt": "2026-01-02T10:00:00Z", "windowDays": 7 },
    "traceId": "01J..."
  }
}
```

- `code` 是給程式判斷的，`message` 是給人看的（且不保證穩定）
- `details` 帶客戶端**需要拿來組訊息或做決定**的資料，不要倒內部狀態
- 參數驗證錯誤帶欄位層級的清單，讓客戶端標在對應輸入框上
- `traceId` 讓使用者回報時查得到

## 領域事件 → 推播 / webhook

- 不是每個事件都要推播。只挑「使用者需要被打斷」的。
- payload 只帶事件類型、資源識別碼、發生時間、去重鍵；**細節讓客戶端回頭查**。推播會遲到、會重複、會被截斷，而且到達時資料可能已經又變了。
- webhook 要定義簽章驗證、重試策略與去重鍵。

## 常見錯誤

| 錯誤 | 後果 |
|---|---|
| 把 schema 的 table 當 response | 內部欄位洩漏，schema 一改就是破壞性變更 |
| 一個 `PATCH` 吃下所有狀態轉換 | 權限與錯誤碼講不清楚 |
| 列舉回數字 | 加一個值就錯位，而且讀 log 看不懂 |
| 金額用浮點數 | 精度錯誤，且與 schema 的定點數不一致 |
| 業務規則失敗回 400 | 客戶端分不出「輸入錯」與「現在不允許」 |
| 錯誤只有 message 沒有 code | 客戶端只能比對字串 |
| 篩選參數開放任意欄位 | 沒有索引支撐的查詢會拖垮資料庫 |
