# 相容性與版本

有行動端時這份是必讀的。**舊版 app 會在使用者手機上待數個月**——你發布的契約不是「目前的介面」，是一份對所有還活著的客戶端版本的承諾。

Web-only 專案可以放寬（前端跟著後端一起部署），但「什麼算破壞性變更」的判準不變。

## 什麼算破壞性變更

對**既有**客戶端會壞掉的，全部是：

| 變更 | 為什麼破壞 |
|---|---|
| 刪除欄位、刪除端點 | 舊客戶端讀不到，可能直接崩潰 |
| 改欄位名 | 等於刪一個加一個 |
| 改欄位型別（含整數 → 字串） | 解析失敗 |
| 可選欄位改必填 | 舊客戶端不會帶 |
| 收緊驗證（長度、範圍、格式） | 以前能送的現在被拒 |
| 列舉**移除**值 | 舊客戶端送的值變非法 |
| 改既有錯誤碼的意義，或改它的 status | 客戶端的處理分支全錯 |
| 改預設值 | 沒帶那個欄位的舊請求行為變了 |
| 改分頁形狀、改排序預設 | 列表顯示錯亂 |
| 把同步操作改成非同步 | 客戶端拿不到結果 |

**不是**破壞性的：

- 新增**可選**的 request 欄位
- 新增 response 欄位（前提：客戶端不做嚴格解析——這條要寫進契約，要求客戶端忽略未知欄位）
- 新增端點
- 列舉**新增**值（前提：契約明寫客戶端遇到未知值要有 fallback，否則新增值也是破壞性的）
- 放寬驗證
- 新增可選的錯誤碼（前提：客戶端對未知錯誤碼有預設處理）

括號裡的前提要寫進契約的「客戶端必須遵守」段。沒有寫，這些就全部變成破壞性變更。

## 客戶端必須遵守

寫進契約，客戶端的實作要照這幾條，否則相容性承諾不成立：

1. **忽略未知欄位**，不要用嚴格模式解析。
2. **未知列舉值要有 fallback**（顯示原始字串或當成「其他」），不要當成解析失敗。
3. **未知錯誤碼走預設處理**（顯示通用訊息 + traceId），不要崩潰。
4. **不要依賴欄位順序**，也不要依賴 `details` 的內容結構。

## 版本策略

三選一，全份統一：

| 策略 | 適用 | 代價 |
|---|---|---|
| **不版本化 + 只做相容變更** | 一人或小團隊、客戶端更新快 | 破壞性變更要等到能淘汰舊版才做 |
| 路徑版本（`/v1/`、`/v2/`） | 需要一次做大改版 | 兩套要同時維護一段時間 |
| header 版本 | 需要細緻控制 | 除錯與快取都比較麻煩 |

**預設推薦不版本化**：相容變更能做的就做相容變更，真的必須破壞時走下面的棄用流程。開 `/v2` 的成本（兩套程式碼、兩套測試、兩套文件）通常比想像的高很多。

## 棄用流程

破壞性變更不可避免時，照這個順序，每一步都要在契約上留紀錄：

1. **新增**新的欄位 / 端點 / 錯誤碼，與舊的並存。
2. **標記**舊的為 `deprecated`，寫明替代品與預計移除的時間或版本。
3. **回報**：伺服器端記錄還有哪些客戶端版本在用舊的（帶 client version header 就能統計）。
4. **等**：等到用量降到可接受，或最低支援版本超過它。行動端的經驗值是**至少兩個發版週期**。
5. **移除**，並記進「變更紀錄」。

跳過第 3 步是最常見的錯誤——沒有數據就只能猜「應該沒人用了」。

## 最低支援版本

契約要寫明：

- 目前支援的最舊客戶端版本
- 低於它的客戶端會收到什麼（強制更新的錯誤碼 + 更新指引）
- 誰決定往上提（這是產品決策，不是 agent 的決策）

強制更新的機制本身要在第一版就放進契約——第一版沒放，之後就永遠沒有辦法要求舊客戶端更新。

## 破壞性變更段

每條寫五件事：

| 欄位 | 內容 |
|---|---|
| 變更 | 具體改了什麼 |
| 影響 | 哪些客戶端版本會壞、怎麼壞 |
| 替代方案 | 客戶端要改成什麼 |
| 棄用期 | 從什麼時候到什麼時候並存 |
| 移除條件 | 滿足什麼條件才真的移除（用量、版本分布） |

答不出「移除條件」的，就還不能開始棄用。
