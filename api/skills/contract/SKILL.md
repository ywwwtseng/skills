# API Contract

`/db:schema` 把模型的**狀態**落成 table，但模型的**命令與查詢**要怎麼被外界呼叫，沒有任何文件回答。於是 `/impl:plan` 排到 API 的 task 時，端點、欄位形狀、錯誤碼全是當場發明的。

跨 context window 的兩個 task（後端與客戶端）會各自發明一份，而且**兩邊測試都會綠**——客戶端的 mock 是照客戶端自己發明的形狀寫的。無人看守時，沒有任何一步會發現這件事。

## 定位：模型與客戶端之間的那一層

- **輸入**：`docs/domain/model/`（命令、查詢、領域事件、權限規則、不變量）、`docs/domain/business-rules/`（每條規則的例外與失敗情境）、`docs/db/schema.md`（不變量落點表——DB 擋住的要翻成錯誤碼）、`docs/architecture/tech-stack.md`（API 風格、認證方式、有哪些客戶端）、既有 API（程式碼、OpenAPI、既有 `contract.md`）。
- **輸出**：單一檔案 `docs/api/contract.md`。跟 schema 一樣不分檔——契約的價值在於一次看見所有端點與錯誤碼。
- **不做**：實作、產生 OpenAPI / TypeScript 型別 / client SDK、DB 設計、UI 規格。本 skill 只產設計文件，檔案生成交給 `/impl:plan` 排成 task。

`/db:schema` 回答「狀態怎麼存、規則由誰執行」；本 skill 回答「外界怎麼呼叫、失敗時回什麼」。兩者都吃同一份模型，互不隸屬。

## 核心規則

1. **模型是唯一來源。** 每個端點都對應模型的一個**命令**或**查詢**，不得憑空新增操作。純傳輸需要的（健康檢查、token 刷新、上傳簽章）可以加，但要標「傳輸衍生」並寫明為什麼非有不可；業務操作缺漏則回報，建議回 `/domain:model` 補，不要在契約層補一個模型沒有的命令。
2. **雙向追溯。** 每個端點、每個非傳輸欄位、每個錯誤碼都要指回模型元素或 `BR-ID`；反過來，模型的每個命令與查詢都要在「命令落點表」找到去處，未落地的列出來並寫原因。
3. **每條規則的失敗情境都要有一個錯誤碼。** BR 寫「超過 7 天不能取消」→ 要有一個可辨識的錯誤碼、一個 HTTP status、一句「客戶端該怎麼處理」。只寫 `400` 不給錯誤碼，等於逼客戶端比對錯誤訊息字串——而訊息會被翻譯、會被改。
4. **契約發布後就是承諾。** 舊版 app 會在使用者手機上待數個月：新增欄位一律可選、不改既有欄位的語意與型別、不收緊既有驗證、不改既有錯誤碼的意義。做不到的列進「破壞性變更」段，照 `references/compat.md` 寫棄用期與最低支援版本。這條在只有 web 客戶端時可以放寬，有行動端時不行。
5. **一個風格，全份一致。** REST / GraphQL / tRPC / gRPC 選一種（`references/styles.md`），錯誤格式、命名、分頁、篩選全部統一。混用會讓客戶端要寫兩套處理。
6. **錯誤回應只有一種形狀。** 全域一個 envelope（錯誤碼、訊息、細節、追蹤 ID），所有端點共用。每個端點各自發明錯誤形狀是客戶端最痛的事。
7. **跟不變量落點表對得上。** `docs/db/schema.md` 說「DB 的 UNIQUE 會擋」的那條規則，契約要寫明它被擋時回哪個錯誤碼。落點表有、契約沒有，就是客戶端會收到一個沒定義的 500。
8. **不改模型、不改 schema。** 設計契約時發現模型缺命令、規則沒定義失敗情境、schema 落點不合理，寫進最相關的 `docs/impl/<feature>/plan.md` 的「上游回饋」表（狀態 `待處理`），交給 `/domain:feedback`。不要自己補一條規則。
9. **提問必須用 `AskUserQuestion`，一次只問一題。** 只問「不同答案會產生不同端點結構」的（一個命令拆成兩個端點還是一個帶模式參數、批次操作要不要支援、查詢要不要做成獨立的讀取模型）。欄位命名、status code 選 400 還是 422 這類事自己決定並寫進慣例段。

## 流程

### Step 0：讀模型、既有契約、決定風格

1. 讀 `docs/domain/model/README.md` 與各聚合檔，整理出三張清單：**命令**（含參數、前置條件、失敗情境）、**查詢**（含篩選與排序需求）、**領域事件**（哪些需要推播或 webhook）。沒有 `docs/domain/model/` 就停，建議先跑 `/domain:model`。
2. 讀 `docs/domain/business-rules/`，把每條規則的**例外與失敗情境**單獨列一張表，Step 3 要逐條指派錯誤碼。
3. 讀 `docs/db/schema.md` 的不變量落點表（核心規則 7）。
4. 盤點既有 API：既有 `docs/api/contract.md`、路由程式碼、OpenAPI 檔。存在就是現況，沿用既有命名與錯誤碼，只做增量（變動記進「變更紀錄」，破壞性的另列）。
5. 決定風格與認證：使用者指定 > 既有 API > `docs/architecture/tech-stack.md` > `AskUserQuestion` 問一題。同時確認**有哪些客戶端**（web / iOS / Android / 第三方），這決定 Step 6 的嚴格程度。

### Step 1：命令與查詢 → 操作清單

依 `references/mapping.md` 逐個轉換：

- 一個**命令** = 一個操作。不要把三個命令塞進同一個 `PATCH`，狀態轉換尤其要各自獨立（`/orders/{id}/cancel` 而不是 `PATCH {status: "cancelled"}`）——前者的錯誤碼與權限講得清楚，後者講不清楚。
- 一個**查詢** = 一個操作，含它需要的篩選、排序、分頁。
- **領域事件**決定要不要推播 / webhook，payload 在 Step 5 定。
- 聚合邊界決定資源層級：聚合根是一級資源，聚合內的實體掛在它下面。

### Step 2：request 與 response

- 欄位名照 `references/styles.md` 的慣例段（全份一種大小寫風格）。
- 每個欄位標：型別、必填或可選、來源（模型元素或「傳輸衍生」）、驗證規則（追溯到 BR-ID）。
- response 只回客戶端**需要**的欄位；不要把 table 整列倒出去（那會讓 schema 的變更直接變成契約的破壞性變更）。
- 分頁、排序、篩選、部分回應的慣例全份統一，寫進慣例段。
- 時間一律 ISO 8601 帶時區、金額照 schema 的單位慣例（最小單位整數或定點字串，不用浮點數）。

### Step 3：錯誤碼

逐條走 Step 0 整理的失敗情境表（核心規則 3），每條產出一列：**錯誤碼 / HTTP status / 何時發生 / 客戶端該怎麼處理 / 來源 BR-ID**。設計準則見 `references/mapping.md` 的錯誤段。

漏掉任何一條規則的失敗情境，就是客戶端沒有辦法正確處理它——列進「未覆蓋」並寫原因，不默默略過。

### Step 4：認證與授權

- 認證方式（token 形式、效期、刷新流程）寫一次，全域套用。
- 模型的**權限規則**逐條落到端點：誰能呼叫、判斷依據是什麼、失敗回 401 還是 403（兩者的差別寫進慣例段）。
- 權限失敗**不要洩漏資源是否存在**（該回 404 還是 403，全份統一一種做法並寫理由）。

### Step 5：傳輸關切

依客戶端類型決定要寫哪幾段（有行動端時全部都要）：

- **冪等**：模型有「重複請求視為同一次」的規則，或任何會扣款、會發訊息的命令 → 冪等鍵放在哪、重複時回什麼。行動網路會斷，同一個請求本來就會送兩次。
- **重試**：哪些錯誤可重試、退避策略、哪些絕對不可重試。
- **限流**：回什麼 status、帶什麼 header。
- **推播 / webhook payload**：對應哪個領域事件、欄位、去重鍵。payload 一律只帶識別碼與最小資訊，細節讓客戶端回頭查（推播不可靠、會遲到、會重複）。
- **檔案上傳 / 下載**：走哪條路徑、大小限制、簽章網址的效期。

### Step 6：相容性與版本

讀 `references/compat.md`，寫出：版本策略（路徑版本 / header / 不版本化）、什麼算破壞性變更、棄用流程與棄用期、最低支援客戶端版本、以及本次的破壞性變更清單（含對舊版客戶端的影響與遷移步驟）。

有行動端時這一段是必寫的（核心規則 4）。

### Step 7：釐清（有結構性歧義才做）

只挑同時符合以下條件的問題：

- 不同選擇會產生**不同的端點結構**（多一個端點、資源層級不同、同步還是非同步）
- 從模型、既有 API、風格慣例**推不出**明顯較合理的一邊
- 選錯後要**改客戶端**才能補救（不是加一個可選欄位就好）

依補救成本排序，一題一題用 `AskUserQuestion` 問。`options` 的 `description` 格式：「契約：〈端點會長怎樣〉／影響：〈客戶端要怎麼呼叫、之後要改時的代價〉」。

### Step 8：輸出

格式見 `references/template.md`，寫入 `docs/api/contract.md`。寫完做四個檢查：

1. **追溯完整性**：每個端點、每個非傳輸欄位、每個錯誤碼都有來源；模型的每個命令與查詢都在落點表裡，未落地的有原因。
2. **錯誤覆蓋**：每條 BR 的每個失敗情境都有錯誤碼；schema 落點表裡由 DB 擋的每一條，都能對到一個錯誤碼（核心規則 7）。
3. **權限覆蓋**：模型的每條權限規則都指派到端點。
4. **風格一致**：命名、分頁、錯誤形狀、status code 用法全份一種做法（核心規則 5、6）。

### Step 9：收尾

在對話中：

1. 寫入 / 修改的檔案與這次動了什麼
2. 規模：端點數、錯誤碼數、事件 / 推播數
3. 覆蓋統計：模型命令 N 個落地 M 個、BR 失敗情境 N 條對應 M 個錯誤碼（未覆蓋的逐條列出原因）
4. **破壞性變更**（若有）與對舊版客戶端的影響
5. 最值得確認的 3 個契約假設
6. 上游回饋（若有），建議跑 `/domain:feedback`
7. 下一步：`/impl:plan` 讀本文件排 task。**多客戶端專案的順序固定是伺服器端先、客戶端後**——契約先實作出來並進 main，客戶端的 feature 才開始，否則客戶端會對著一份還沒實現的文件寫程式

## 判斷準則

- `references/mapping.md`：命令 / 查詢 / 事件 → 操作的對應細則、欄位與型別、錯誤碼設計與 status code 選擇、常見錯誤（Step 1–3 必讀）
- `references/styles.md`：REST / GraphQL / tRPC / gRPC 的落地方式與各自的錯誤、分頁、版本做法（Step 0 決定風格後必讀對應段）
- `references/compat.md`：什麼算破壞性變更、棄用流程、最低支援版本、行動端的相容性紀律（Step 6 必讀）
- `references/template.md`：`docs/api/contract.md` 的輸出模板（Step 8 必讀）

## 常見失敗模式

| 症狀 | 為什麼是錯的 |
|---|---|
| 把 table 整列當成 response | schema 改一個欄位就變成契約的破壞性變更（Step 2） |
| 狀態轉換做成 `PATCH {status}` | 每個轉換的權限與錯誤碼講不清楚，客戶端也不知道哪些轉換合法（Step 1） |
| 失敗只回 `400` 加一句訊息 | 客戶端只能比對字串，而訊息會被翻譯、會被改（核心規則 3） |
| 每個端點各自發明錯誤形狀 | 客戶端要為每個端點寫一套處理（核心規則 6） |
| 為了方便改了既有欄位的型別 | 舊版 app 直接崩潰，而它還會在手機上待三個月（核心規則 4） |
| 契約裡新增一個模型沒有的操作 | 那個操作沒有規則、沒有人知道它該做什麼（核心規則 1） |
| 推播 payload 帶完整資料 | 推播會遲到、會重複、會被截斷；帶識別碼讓客戶端回頭查（Step 5） |
| 寫完契約就讓客戶端與伺服器端同時開工 | 客戶端對著還沒實現的文件寫，整合時才發現落差（Step 9） |
