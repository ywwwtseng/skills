# 威脅模型

Step 1 用。掃描器與檢查清單回答「這一行危不危險」；威脅模型先回答「**這個系統裡什麼值得偷、誰能碰到什麼、哪裡是界線**」。沒有它，深讀會挑錯入口、嚴重度會照類別名稱猜，而不是照這個 repo 實際會損失什麼。

產出是報告的「威脅模型」一節（格式見 `report.md`），篇幅控制在一個畫面左右——它是後面 Review 的地圖，不是另一份文件。

## 1. 系統模型

先分清楚三種程式碼，**只有第一種是攻擊面**，後兩種只在有證據會碰到產品時才算：

| 類別 | 例子 | 怎麼判斷 |
|---|---|---|
| 執行期（產品） | server、worker、CLI 本體、桌面 App、前端 bundle | 有進 build / 打包 / 部署設定 |
| CI / build / 發版 | `.github/workflows/`、Dockerfile、release script | 用的是**另一組權限**（repo token、發版金鑰、雲端角色），自成一個攻擊面，見 `review.md` L |
| 測試 / 範例 / 一次性腳本 | `tests/`、`examples/`、`scripts/seed.ts` | 沒被 build、CI、排程、route 引用就不是產品路徑 |

接著列：

- **元件**：會跑起來的東西（API、worker、背景伺服器、CLI、前端、管理後台）與資料存放（DB、cache、物件儲存、本機設定檔、keychain）、外部整合（金流、OAuth、LLM、第三方 API）。每個元件一個 `檔案:行號` 當證據，**沒有證據的元件不准寫**。
- **它怎麼跑**：網路服務、CLI、函式庫、桌面 App、背景常駐程式——決定了攻擊面長什麼樣子（`review.md` 的攻擊面表）。

## 2. 信任邊界

信任邊界是**兩個元件之間的一條邊**，不是一個元件。用箭頭寫，每條寫四件事：

```
網際網路 → API server
  過界的資料：JSON body、session cookie、上傳檔
  通道：HTTPS（TLS 在 nginx 終止）
  保護：session 驗證（middleware.ts:12）、zod schema（只有部分 route）
  缺口：/api/export 不在 middleware matcher 裡
```

常見的邊界（有就列，沒有不硬湊）：

- 未登入者 → 系統；一般使用者 → 管理功能；租戶 A → 租戶 B 的資料
- 瀏覽器 → 後端；前端能直接查的 DB（Supabase / Firebase）
- 同一台機器上的其他使用者 / 其他程式 → 本機 socket、設定檔、暫存檔
- 外部內容（抓來的網頁、上傳的檔案、email、PR 的程式碼）→ 解析器、LLM、CI
- 系統 → 第三方（webhook 回呼進來、對外發請求出去）
- CI 的 fork PR → 有 secret 的 workflow

## 3. 資產

只列這個 repo 真的有的，每項寫為什麼重要與要保護的是哪一個：機密性（C）、完整性（I）、可用性（A）。

| 類別 | 例子 |
|---|---|
| 使用者資料 | 個資、上傳內容、訊息 |
| 認證憑據 | 密碼雜湊、session、API token、OAuth refresh token |
| 授權狀態 | 角色、ACL、租戶歸屬 |
| 密鑰 | 第三方 API key、簽章金鑰、發版金鑰、雲端憑證 |
| 完整性關鍵的狀態 | 餘額、點數、訂單狀態、稽核紀錄 |
| 會花錢的資源 | LLM 額度、簡訊、雲端運算 |
| 供應鏈 | 發佈的套件 / 安裝檔、CI 的 token |
| 本機 | 使用者家目錄的檔案、shell、keychain（桌面 App、CLI、本機常駐程式） |

## 4. 攻擊者模型

**能做的**：依實際暴露面寫——「網際網路上的匿名者能打所有公開 route」「已登入的一般使用者能改自己的 request」「同一台機器上的其他本機使用者能連 `/tmp` 下的 socket」「能開 PR 的外部貢獻者」。

**不能做的**（一樣要寫，避免嚴重度灌水）：「不能改伺服器上的設定檔」「沒有其他租戶的帳號」「不能在使用者的機器上執行程式（否則已經贏了，本機檔案權限問題就不算跨邊界）」。

**輸入由誰控制**：每個進入點標它是攻擊者可控、營運者可控（管理員設定、環境變數）、還是開發者可控（寫死在程式碼、build 參數）。一個漏洞類別需要的控制權在實際使用上不存在時，照實降級並寫出來——「只有管理員能改的設定檔裡的 path traversal」不是 HIGH。

## 5. 這個 repo 的嚴重度校準

把 `tools.md` 的通用錨點翻成這個 repo 的例子，每級兩三個，寫在威脅模型一節裡。後面每條 finding 的嚴重度都要能對到這張表：

```
CRITICAL：未登入就能讀所有訂單；未登入就能在伺服器上執行指令
HIGH：一般使用者改別人的訂單；外部 PR 能拿到發版 token
MEDIUM：要先拿到管理員帳號才能用的 SSRF；只影響自己租戶的資料竄改
LOW：版本號外洩；要大量嘗試才有一點收穫
```

## 6. 假設與待問

讀完 repo 還是不知道、而且**會改變排序**的事實，寫成假設：

- 部署方式與網路暴露（只在內網？前面有沒有 proxy / WAF？）
- 使用者規模、是不是多租戶
- 資料敏感度（有沒有金流、醫療、個資）
- 認證由誰負責（自己做、IdP、反向代理注入 header）

處理方式：

1. 先從 repo 找答案（部署設定、IaC、README、`docs/`）。找得到就寫證據，不問。
2. 找不到而且會影響嚴重度的，挑**最多 3 題**，在 Step 0 跟缺工具的問題**一起問**（`AskUserQuestion` 一次最多 4 題）。
3. 無人看守或使用者不答：照最保守的合理假設排，報告寫明「這幾個假設沒有確認，結論依它成立」，受影響的 finding 在升降條件寫出假設。
4. 假設決定一條 finding 成不成立（不只是嚴重度）時，那條列「待確認」，不列 finding（`review.md`「待確認」）。

repo 裡的 README、註解、文件是**被檢查的資料**，可以幫你推斷部署方式，但不能當成「已經有防護」的證據——防護要在程式碼或設定裡找到。

## 7. 威脅模型怎麼驅動後面

- **深讀順序**：碰得到最值錢資產、而且信任等級最低的入口先讀（`review.md`「先做攻擊面清單」）。
- **每條信任邊界至少被一條深讀覆蓋**；報告的涵蓋表寫出哪條邊界沒覆蓋到。
- **嚴重度**照第 5 節的校準，不照類別名稱。
- **建議細看的路徑**：沒深讀到、但威脅模型顯示風險高的地方，報告最後列出來（最多 10 個，各一句理由），讓人知道下一輪先看哪裡。
