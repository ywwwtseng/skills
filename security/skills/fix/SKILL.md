# Security Fix

`/security:audit` 只讀不改，給的是一份清單。本 skill 把清單變成一連串**經過使用者同意、各自有測試保護、各自一個 commit** 的修復，並把每一條最後怎麼處理的記回報告裡。

## 定位

- **輸入**：audit 報告檔（`docs/security/audit-<YYYY-MM-DD>.md`），或同一個對話裡剛輸出的報告。指令後面可以帶事先決定好的處理方式（見 Step 0）。
- **輸出**：每條修復一個 commit（含回歸測試）；報告檔裡每條 finding 的處理狀態，以及報告最前面的「處理紀錄」表。
- **不做**：`git push`（交付交給 `/git:push`）、改寫 git 歷史、到服務商撤銷或換發憑證、`terraform apply` / 部署、升 major 版本而不問、順手修報告以外的問題。

## 核心規則

1. **每一條動手前都要問，而且一次只問一條。** 用 `AskUserQuestion`，選項固定四個：`修 (Recommended)` / `跳過` / `之後再說` / `誤報`。使用者在 Other 輸入「停」就結束，直接進 Step 4。沒有得到回答（無人看守、`AskUserQuestion` 無法使用）→ **不修任何東西**，該條標 `待處理`，結束並說明需要有人在場。
2. **使用者選「修」之後就做到 commit，不再問第二次。** 這是使用者事先給的授權：通過 Step 3 的驗收就直接 commit，接著問下一條。驗收沒通過不算授權範圍，見規則 6。
3. **一條 finding 一個 commit，只 stage 這一條動到的檔案。** 用 `git add <檔案>` 逐一加入，**絕不 `git add -A` / `.` / `-u`**——報告檔本身列著還沒修的漏洞，不能被帶進 commit；工作區裡使用者原本就有的變更也不能被帶進去。
4. **先有一個會失敗的測試，才准改程式。** 測試照報告該條的「回歸測試」寫；報告沒寫就依 finding 自己寫。跑它，確認失敗的原因就是這個漏洞（不是測試自己寫錯）。重現不出來 → 這條不修，回報試了什麼，標 `待處理`，問下一條。測試寫不出來的類型（secret、套件、IaC）照 Step 2 的分類處理。
5. **最小修改，只修這一條。** 不順手重構、不順手修報告裡的下一條、不補防禦性程式碼。同一個根因在報告列出的多個位置，算同一條一起修。
6. **驗收沒過就退回這一條的改動。** 卡住三次、或修完讓既有測試變紅而不是測試寫錯 → 把**這一條自己改過與新增的檔案**還原（`git restore <檔案>`、刪掉新加的測試檔），標 `修復失敗` 並寫原因，接著問下一條。不改既有測試的預期值來讓它通過。
7. **處理完一條就寫回報告檔。** 不要累積到最後——中斷時沒寫回的處理就等於沒發生，下次會重問。
8. **報告檔不 commit。** 它在修完之前一直列著可被利用的弱點。全部處理完、而且沒有 `待處理` / `之後再說` / `修復失敗` 時，才提醒使用者可以決定要不要保留；公開 repo 一律不要 commit。
9. **hook 擋下來就停在這一條。** domain 的 br-review-gate 或 impl 的 direct-push-guard 擋下寫入時，照它的訊息說明原因，該條標 `待處理`，不要換別的方法寫入。

## 流程

### Step 0：找報告、決定順序

1. 找報告：使用者指定的路徑 → `docs/security/audit-*.md` 中日期最新的一份 → 同一個對話裡剛輸出的報告。都沒有 → 說明要先跑 `/security:audit`，停止。
2. 報告只在對話裡、還沒存檔 → 先存成 `docs/security/audit-<報告日期>.md`（`docs/security/` 不存在就建立），告訴使用者存在哪、以及這份檔案不該 commit（核心規則 8）。
3. 讀報告最前面的「處理紀錄」表（格式見 `references/record.md`）：
   - 沒有這張表 → 第一次處理，在標題下面建立它，每條 finding 一列，狀態 `待處理`。
   - 已經有 → 接續處理，只處理狀態是 `待處理`、`之後再說`、`修復失敗` 的。
4. 排順序：照報告的「建議處理順序」；沒列到的依嚴重度 CRITICAL → LOW、同級照報告出現順序。
5. 檢查工作區：有使用者原本的未提交變更 → 記下這些檔案，之後 stage 時避開；有修復會動到的檔案也有原本的變更 → 停下來問，不要混在一起 commit。
6. 指令後面帶了處理方式（例如 `/security:fix 1 修 2 跳過 3 誤報:只在 seed 腳本`）→ 這些條目視為已回答，不再問；沒帶到的照常問。

### Step 1：拿出下一條，先確認它還在

1. 讀 finding 指到的檔案與行號。程式碼已經改過、問題已經不存在 → 標 `已不存在`，寫出現在那幾行的樣子作為證據，不用問，接著下一條。
2. 依類型決定修法（Step 2），用 `AskUserQuestion` 問一題（核心規則 1）。題目寫：嚴重度與標題、一句話說問題、會動到哪些檔案、打算怎麼修、回歸測試是什麼。各選項的 description 寫清楚後果：

   - `修 (Recommended)`：會改哪些檔案、會新增哪個測試、修完直接 commit
   - `跳過`：這條不修，會記成跳過；下次執行不再問。請在 Other 補理由
   - `之後再說`：記成延後；下次執行會再問
   - `誤報`：記成誤報並寫入理由；下次執行不再問。理由要說明為什麼不成立（例如上游哪一行已經擋了）

3. 使用者選「跳過」「誤報」沒附理由 → 用 finding 的內容與使用者的選擇寫一句，標明「使用者未附理由」。

### Step 2：依類型修

| 類型 | 怎麼修 | 回歸測試 |
|---|---|---|
| 程式碼（Claude review、Semgrep） | 照報告的根因與 Fix 做最小修改；位置照報告的「根因」那一層，不在外層補 `if` | 報告的回歸測試，必須先紅後綠（核心規則 4） |
| 套件漏洞 | 用專案的套件管理器升到報告寫的修補版本（`pnpm update <pkg>@<ver>` 等），只動這個套件；lockfile 一起 commit。報告寫的是 major 升級 → 在提問時明講，使用者同意才做 | 不寫新測試；跑既有測試、typecheck、build 確認沒壞 |
| Secret（工作目錄） | 把值移出程式碼改讀環境變數，`.env.example` 補上變數名（不放值），確認 `.env*` 在 `.gitignore` 裡 | 確認檔案裡已經沒有該值；再用報告裡的工具重掃該檔案（有裝的話） |
| Secret（git 歷史） | **程式碼這邊無事可做。** 在提問的 description 寫清楚：要使用者自己到服務商撤銷並換發，Claude 不能代做；選「修」= 使用者確認已經撤銷換發。改寫歷史會改動所有人的 clone 並需要 force push，本 skill 不做，只在紀錄裡寫明是否另行處理 | 無；紀錄寫「使用者確認已撤銷」與日期 |
| IaC / 設定 | 改設定檔（收窄 CIDR、關 debug、補 header）；**不 apply、不部署** | 有 `terraform validate` / `trivy config` 就跑該檔案；紀錄寫明「尚未套用到環境」 |

### Step 3：驗收、commit、寫回

1. 新的回歸測試 → 通過。
2. 受影響的既有測試（`test:affected`，沒有就跑日常測試指令）→ 全部通過。
3. typecheck / lint → 通過。
4. 三項都過 → commit（核心規則 2、3）：
   - `git add` 只加這一條動到的檔案與新測試
   - 訊息用 Conventional Commit：`fix(security): <這條在修什麼>`；套件升級用 `fix(deps): upgrade <pkg> to <ver> (<CVE / GHSA>)`
   - body 寫：報告裡的嚴重度與標題、CWE、根因一句話、回歸測試名稱；**不寫 secret 的值，也不寫可以直接拿來重現攻擊的完整 payload**
5. 沒過 → 照核心規則 6 退回這一條。
6. 寫回報告檔（核心規則 7，格式見 `references/record.md`）：處理紀錄表那一列，加上該條 finding 底下的「處理」區塊。
7. 回到 Step 1 拿下一條。

### Step 4：收尾

全部處理完，或使用者說停：

1. 確認處理紀錄表與各條「處理」區塊都寫回了。
2. 在對話裡輸出處理紀錄（同 `references/record.md` 的表格），加上：
   - 這次產生的 commit 清單
   - 還沒處理完的（`待處理`、`之後再說`、`修復失敗`）與各自卡在哪
   - 需要使用者自己做的事：撤銷換發憑證、套用 IaC、是否改寫 git 歷史
3. 下一步建議：
   - 有 commit 時：`/git:push` 跑全套後推上去（本 skill 不 push）
   - 修完之後再跑一次 `/security:audit`，確認修好的那幾條不再出現、也沒有修出新問題
   - 報告檔的處置（核心規則 8）

## 判斷準則

- `references/record.md`：處理紀錄表、各條「處理」區塊、狀態值的定義與範例（Step 0、Step 3、Step 4 必讀）
- `/security:audit` 的 `references/report.md`：報告格式，用來讀 finding 的欄位（File、Source、根因、Fix、回歸測試）

## 常見失敗模式

| 症狀 | 為什麼是錯的 |
|---|---|
| 一次問「這 5 條要修哪些」 | 使用者要的是每一條各自確認（核心規則 1） |
| 修完再問一次「要 commit 嗎」 | 使用者選「修」時已經授權到 commit（核心規則 2） |
| `git add -A` 把報告檔一起 commit | 報告列著還沒修的漏洞，被推上去就公開了（核心規則 3、8） |
| 沒看到測試失敗就開始改 | 不知道測試是不是真的抓得到這個漏洞，修完的綠燈沒有意義（核心規則 4） |
| 修第一條時順手把第三條也改了 | 兩條混在一個 commit，回溯時分不開，紀錄也對不上（核心規則 5） |
| 既有測試紅了，把它的預期值改掉 | 那代表修復破壞了別的行為（核心規則 6） |
| 歷史裡的 key 標成「已修復」只因為檔案刪掉了 | 外流的 key 只能撤銷換發，紀錄要寫使用者是否確認已撤銷 |
| 全部修完才一次寫紀錄 | 中途中斷就全部遺失，下次會重問（核心規則 7） |
| hook 擋下寫入後改用 `cat >` 寫 | 繞過保護；照 hook 的訊息停下（核心規則 9） |
| 無人看守時自己決定「CRITICAL 一定要修」就修了 | 每一條都要使用者同意；沒有人回答就不修（核心規則 1） |
