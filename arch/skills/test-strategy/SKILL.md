# Test Strategy

`/impl:feature` 負責寫測試、`/impl:verify` 負責查測試。但沒有人決定**該寫哪一層的測試**，也沒有人搭好**讓那一層測試跑得起來的環境**。結果通常是整個專案只有 mock 掉資料庫的單元測試：`docs/db/schema.md` 寫明由 DB 擋的唯一約束、CHECK、交易與並行從來沒有被真的驗過，而 `/impl:verify` 依然判定「有覆蓋」。

本 skill 補的就是這一塊：定分層、建環境、在開發中的專案裡先把保護網補到可以放心改動的程度。

## 定位：骨架之後、第一個 feature 之前（可重複執行）

- **輸入**：`docs/architecture/tech-stack.md`（技術棧、約束與慣例）、`docs/db/schema.md`（不變量落點表）、`docs/domain/business-rules/`、`docs/domain/model/`、`docs/api/contract.md`、`docs/ui/screens/`（有的話）、`docs/impl/debt.md`（「需先補測試」的項目），以及**既有程式碼與測試**。
- **輸出**：`docs/architecture/testing.md`、測試基礎設施（指令、測試資料庫設定、共用 setup、fixture 目錄、CI 步驟）、`CLAUDE.md` 的測試慣例段落；開發中的專案另外有新增的特徵測試（characterization test）。
- **不做**：改產品程式碼、改或搬移既有測試、換測試框架、修 bug、連線到任何非本機的資料庫、commit。

跟其他 skill 的分工：

| 誰 | 回答什麼 |
|---|---|
| `/arch:init` | 測試框架裝好、一個範例測試會過 |
| **本 skill** | 哪類規則用哪一層驗、那一層的環境怎麼搭、既有程式碼先補哪裡 |
| `/impl:plan`、`/impl:feature` | 依 `testing.md` 為每個 task 寫對的那一層測試 |
| `/impl:verify` | 依 `testing.md` 檢查測試層級對不對，不只是有沒有 |
| `/impl:fix` | 修本 skill 發現的疑似缺陷 |
| `/impl:refactor` | 在本 skill 補好的保護網下重構 |

## 三種模式

Step 0 偵測後決定走哪一條，在報告裡寫明判定結果與依據：

| 模式 | 判定 | 走法 |
|---|---|---|
| **A. 新專案** | 還沒有業務程式碼（只有 scaffold 與 `/arch:init` 的範例測試） | 從上游文件推出目標策略 → 建基礎設施 |
| **B. 開發中、已有測試** | 有業務程式碼，也有業務相關的測試 | 盤點現況 → 對照目標找出分層差距 → 補缺的基礎設施 → 依風險補測試 |
| **C. 開發中、零測試** | 有業務程式碼，沒有任何業務測試（沒有框架，或只有範例測試） | 建測試框架 → 從最外層補特徵測試 → 依風險補 → 其餘列入差距清單 |

還沒有 scaffold（沒有 `package.json` / `pyproject.toml` / `go.mod`）→ 停下來，建議先跑 `/arch:init`。

`docs/architecture/testing.md` 已存在 → **更新模式**：保留既有決策，只補新出現的不變量、錯誤碼、差距，並更新差距清單的狀態。不要重寫整份。

## 核心規則

1. **先量基準，基準是紅的就停。** 動手前把既有測試全部跑一次。有紅的（包含偶爾紅的）→ 回報哪些、錯誤訊息是什麼，然後停下來問。不要在壞掉的基準上加東西，也不要順手修——之後任何一條紅都分不清是誰造成的。
2. **不改產品程式碼。** 能動的只有測試檔、測試用設定（測試 setup、測試資料庫設定、`docker-compose` 的測試服務、`package.json` 的測試 scripts）與 CI。某段程式碼不改結構就測不了 → 改從更外層測（見規則 5），並把「可測性」記成一筆債交給 `/impl:refactor`。
3. **不改、不搬、不刪既有測試，不換框架。** 既有測試分層放錯（例如 DB 約束只用 mock 驗）→ 列進差距清單，新增一個對的測試，舊的留著。想換框架是另一個決策，要另外問，不在本 skill 內做。
4. **測試只描述行為，不修行為。** 補測試時發現程式跟規則不符：
   - 有 BR 可對照、程式做的跟 BR 不同 → **不要**寫一個斷言現況的測試把 bug 鎖死，也不要寫一個會紅的測試留在 repo 裡。記進 `testing.md` 的「疑似缺陷」，交給 `/impl:fix`（它會自己寫會紅的 regression test）。
   - 沒有 BR 可對照 → 照現況寫特徵測試，測試名稱或註解標明「記錄現況，非規格」；看起來明顯不對的同樣記進「疑似缺陷」。
5. **由外往內補。** 開發中的專案（尤其模式 C）先補不需要改程式碼就能測的層：打 API、跑 CLI、接真的測試資料庫。這一層寫得出來，之後 `/impl:refactor` 才有保護網把程式拆成可以單元測試的形狀。
6. **分層依不變量落點決定，不依習慣。** `docs/db/schema.md` 寫落點是 DB 約束的，測試一定要打到真的資料庫——mock 掉資料庫等於沒測。對照表見 `references/layers.md`。
7. **測試資料庫只能是本機或容器。** 連線字串判斷不出來是本機（`localhost` / `127.0.0.1` / 容器服務名 / 檔案型 SQLite）就停。測試會清資料，指錯一次就是事故。
8. **依風險補，不追覆蓋率。** 優先順序：金額與計算 → 權限 → 狀態轉換 → 資料寫入與約束 → `git log` 裡最常被改的檔案 → `debt.md` 標「需先補測試」的項目。一次跑不完的列進差距清單，不要為了數字寫一堆斷言 getter 的測試。
9. **新測試要跑兩次都綠。** 整套連跑兩次，支援的話第二次打亂順序。只綠一次的測試在 `/impl:ship` 的無人看守迴圈裡會變成假的 `blocked` 或觸發 `/impl:fix` 去修不存在的 bug。
10. **新依賴只限測試工具，而且要列出來。** 測試框架、測試容器、HTTP 測試客戶端、E2E 工具可以加，加之前在對話列出套件與理由；模式 C 沒有 `tech-stack.md` 可依據時，框架選擇先用 `AskUserQuestion` 確認。
11. **提問用 `AskUserQuestion`，一次一題。** 只在規則 1（基準紅）、規則 10（沒有依據選框架）、以及模式判定不出來時問。其餘照證據與 `references/layers.md` 的預設做，並在報告裡寫理由。
12. **不 commit。** 完成後建議 `/git:commit`。

## 流程

### Step 0：盤點與判定模式

1. 讀 `docs/architecture/tech-stack.md`、`docs/db/schema.md`、`docs/domain/`、`docs/api/contract.md`、`docs/ui/screens/`、`docs/impl/debt.md`、既有的 `docs/architecture/testing.md`（存在的話）。缺的記下來，不擋路——沒有上游文件時改從程式碼推（Step 1）。
2. 盤點測試現況：
   - 框架與設定：`vitest.config.*`、`jest.config.*`、`pytest.ini` / `pyproject.toml [tool.pytest]`、`*_test.go`、`playwright.config.*`
   - 測試檔：`**/*.test.*`、`**/*.spec.*`、`**/test_*.py`、`**/*_test.go`、`__tests__/`、`tests/`
   - 指令：`package.json` scripts、`Makefile`、CI workflow 裡實際跑的測試步驟
   - 每個測試檔粗分層級：有沒有 mock 資料庫 client、有沒有起 HTTP server、有沒有接真的 DB
3. 判定模式（上面的表）。判定不出來時問。
4. **量基準**（核心規則 1）：跑既有的全部測試。模式 C 沒有測試可跑則略過，但要確認 `typecheck` / `build` 是綠的——連 build 都不過，補測試也跑不起來。

### Step 1：決定分層策略

建立「規則類型 → 測試層」對照表，這是 `testing.md` 的核心。依 `references/layers.md` 的預設，逐項走：

1. **不變量**：`docs/db/schema.md` 落點表的每一條。落點 DB → 整合層（真的資料庫）；落點應用層 → 單元層（模型）+ 至少一條整合層確認沒被繞過。
2. **狀態機**：`docs/domain/model/` 的每個狀態機。合法與非法轉換在單元層；持久化後的狀態與並行轉換在整合層。
3. **BR 類別**：計算 / 約束 → 單元層；權限 → API 層（要經過真的認證中介層）；時間 → 單元層並注入時鐘；副作用（寄信、推播、webhook）→ 整合層並替換外部邊界。
4. **契約錯誤碼**：`docs/api/contract.md` 每個錯誤碼至少一條 API 層測試。
5. **畫面狀態**：`docs/ui/screens/` 的關鍵流程（通常是每個 feature 的 happy path 加一個錯誤路徑）走 E2E；其餘狀態用元件測試。E2E 刻意少，因為它慢而且最容易不穩定。
6. **mock 邊界**：只替換「不是我們的、而且測試時不能真的呼叫」的東西——金流、寄信、第三方 API、系統時間。資料庫、自己的模組、自己的 HTTP 層一律不 mock。

沒有上游文件時從程式碼推：migration 裡的 `UNIQUE` / `CHECK` / 外鍵就是 DB 不變量，錯誤處理裡的錯誤碼就是契約，`if` 擋下來丟錯的就是約束規則。在 `testing.md` 標明「無上游文件，依程式碼推導」。

### Step 2：建測試基礎設施

只建對照表用得到的層，不要預先把 E2E 搭好卻沒有任何 E2E 要寫。

1. **指令**：分層拆開，而且每一條都能單獨跑、能指定單一檔案。
   - `test`：跑全部（CI 與 `/impl:feature` 的「既有測試不能壞」用這條）
   - `test:unit`、`test:integration`、`test:e2e`：依對照表需要才建
   - 既有的 `test` 指令已經有人在用 → 保持它的語意（通常就是全部），新增的只加不改
2. **測試資料庫**（有整合層時）：依 `references/layers.md` 選隔離方式（交易回滾 / 每個 worker 一個 schema / 測試容器），寫好 setup 與 teardown，migration 在測試啟動時套用。連線字串遵守核心規則 7。
3. **fixture / factory**：定一個位置與命名（例如 `tests/factories/`），寫一個示範用的 factory。factory 產出的資料要滿足模型的不變量——不合法的資料由測試自己明確覆寫，不要讓預設值就是壞的。
4. **CI**：在既有 workflow 加上對應步驟；整合層需要資料庫就加 service container。沒有 CI 的專案不自行新建（那是 `/arch:init` 的範圍），寫進報告。
5. 每建完一層，跑一次該層指令，確認是綠的再往下。

### Step 3：補測試（模式 B、C）

模式 A 跳過——新專案的測試由 `/impl:feature` 隨 task 寫。

1. **列出候選**：模式 B 是 Step 1 對照表與 Step 0 現況的差距（該在整合層卻只有 mock 的不變量、沒有任何測試的錯誤碼、只測合法轉換的狀態機）；模式 C 是整個程式碼的對外入口。加上 `debt.md` 標「需先補測試」的項目。
2. **依風險排序**（核心規則 8），挑前面的補。預設補到**前 5 個風險區塊**有外層保護為止；使用者指定範圍就照範圍。
3. **逐個補**：
   - 由外往內（核心規則 5）：模式 C 一律先寫 API / 整合層的特徵測試。
   - 有 BR 的：斷言照 BR 的「輸入 → 預期結果」寫，測試名稱帶 BR-ID。跑起來紅 → 刪掉這個測試、記進「疑似缺陷」（核心規則 4），不要留紅的測試、也不要把斷言改成現況。
   - 沒有 BR 的：斷言照現況寫，標「記錄現況，非規格」。
   - 每補一個區塊跑一次全套，既有測試不能變紅。
4. 沒補到的留在差距清單，每一條寫明：哪個區塊、缺哪一層、風險、建議由誰補（屬於某個進行中 feature → 那個 feature 的 `plan.md` 接新 task；否則留在清單上，下次跑本 skill 或排進 `/impl:plan`）。

### Step 4：寫文件

1. 寫入 `docs/architecture/testing.md`（模板見 `references/template.md`）：模式、分層對照表、指令、測試資料庫與隔離、fixture 慣例、mock 邊界、差距清單、疑似缺陷。
2. `CLAUDE.md` 附加 `## 測試慣例` 段（已存在就更新該段，不動其他內容），只放每個 session 都需要的幾行：各層指令、DB 不變量一定要打真的資料庫、mock 邊界、fixture 位置，並連到 `testing.md`。理由跟 UI 風格寫進 `CLAUDE.md` 一樣：`/impl:feature` 寫測試前不一定會去讀 `testing.md`，但 `CLAUDE.md` 一定已經在 context 裡。
3. 有 `docs/impl/debt.md` 時：這次補好測試的項目，把「測試保護」欄更新成實況，狀態從「需先補測試」改回「待處理」，讓 `/impl:refactor` 下一輪可以處理。

### Step 5：驗證

1. 每一條測試指令實跑。
2. 全套連跑兩次，第二次打亂順序（Vitest `--sequence.shuffle`、pytest `-p random_order`、`go test -shuffle=on`，工具不支援就跑兩次）。兩次都要綠（核心規則 9）。不穩定的測試找出原因修掉（通常是共用資料、時間、順序依賴）；修不掉就刪掉並記進差距清單，不要留下。
3. `typecheck`、`lint` 不能因為新增的測試檔變紅。

### Step 6：收尾

在對話中回報：

1. 判定的模式與依據
2. 基準：既有測試數量與結果（模式 C 寫「無」）
3. 分層對照表摘要：幾類規則、各落在哪一層
4. 建了哪些基礎設施、新增哪些依賴
5. 補了哪些測試（模式 B、C）：區塊、層級、數量
6. 疑似缺陷：每條一句話，建議 `/impl:fix`
7. 差距清單還剩幾條、最高風險的是哪幾條
8. 下一步：`/git:commit` 提交；有疑似缺陷先 `/impl:fix`；新專案接 `/domain:business-rules` 或 `/impl:plan`

## 常見失敗模式

| 症狀 | 為什麼是錯的 |
|---|---|
| 基準有紅的，先修掉再開始 | 修 bug 不是本 skill 的工作，而且之後分不清哪條紅是誰造成的（核心規則 1） |
| 為了好測，把 handler 裡的邏輯抽出來 | 在沒有保護網的情況下改產品程式碼，正是要避免的盲改（核心規則 2） |
| 補測試時發現 bug，把斷言寫成現況讓它綠 | bug 被測試鎖死，之後修它的人會以為自己改壞了東西（核心規則 4） |
| DB 唯一約束用 mock 的 repository 測 | 測到的是 mock，不是約束；上線照樣重複寫入（核心規則 6） |
| 測試連到 `.env` 裡的開發共用資料庫 | 測試會清資料（核心規則 7） |
| 模式 C 一口氣把整個專案補到 80% 覆蓋率 | 補的多半是好寫的測試，不是會壞的地方；風險區塊反而沒補到（核心規則 8） |
| 新測試跑一次綠就收工 | 不穩定的測試會在無人看守時冒充成 bug（核心規則 9） |
| 把既有的 mock 測試改成接真的 DB | 改了別人的測試；新增一條整合測試，舊的留著（核心規則 3） |
| E2E 什麼都測 | 慢、不穩定、壞了難定位；E2E 只走關鍵流程 |
